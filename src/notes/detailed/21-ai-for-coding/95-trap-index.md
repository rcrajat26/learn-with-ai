This file indexes the whole guide rather than teaching anything new. Four tables: every `**Pitfall:**`
consolidated (§5.2.1), every place a widely-repeated or syllabus-stated claim turned out to be
version-stale (§5.2.2), the five traps worth knowing with nothing else (§5.2.3), and every real
incident with its cost and its law (§5.2.4).

**Method.** `grep -rn '\*\*Pitfall:\*\*'` across every subfolder found **167 matches**; after removing
two purely meta references (the marker-naming note and the divergence table in `00-index.md`, both
folded into §5.2.2 instead), two "folded into the pitfall above" cross-references that name no new
belief, and one "no gotcha beyond the one already stated," **154 distinct trap rows survive** below —
a handful of near-duplicate restatements across sibling files (`governance/02-…`,
`governance/03-…`) were merged into one row citing both paths. That is well above the ~45 the prompt
estimated, because the callout is used for every wrong belief a leaf surfaces, not only for leaves
carrying the `[TRAP]` tag specifically. `[INCIDENT]` leaves were grepped the same way; ten distinct
incidents survive against the syllabus's estimate of eleven — see §5.2.4's note.

## §5.2.3 — The top five, for the reader with ten minutes

**Rules are enforced by the harness, not the model.** A `CLAUDE.md` line, however forcefully worded
("ENFORCE ALWAYS," "MUST"), shapes what the model *tries* to do; it is never a hard boundary, because
the model is the thing being asked to comply, not the thing checking compliance. A `permissions.deny`
rule, a `PreToolUse` hook that inspects the actual tool call, and the sandbox all sit outside the
model's own turn and evaluate the call itself — that is the entire difference between a guideline and
a guarantee. One-line answer: **if an outcome must hold regardless of what the model decides, it has
to be a settings rule or a hook, never a sentence in a prompt.**

**`deny` cannot carry exceptions.** There is no negation operator in the permission rule syntax — you
cannot write "deny all AWS commands except `s3 ls`." Writing a broad `deny` and then an `allow`
carve-out does not work, because `deny` is checked first and unconditionally: once it matches, `allow`
is never reached, restart or not. One-line answer: **the only way to carve out an exception is to
narrow the `deny` rule itself** — enumerate the specific dangerous subcommands rather than denying the
whole family and trying to allow one back in.

**`allowed-tools` pre-approves rather than restricts.** The word "allowed" reads as an exhaustive
whitelist in ordinary English, but a skill's `allowed-tools: [Read]` only means "skip the permission
prompt for `Read`" — it does nothing to the rest of the tool set, which stays exactly as available as
the session's own broader permissions already made it. A skill fenced this way can still call `Bash`
and delete a directory with no warning. One-line answer: **use `disallowed-tools`, or a
`permissions.deny` rule for a guarantee that holds even against a hostile skill body — `allowed-tools`
is not that guarantee.**

**`--setting-sources` resolves against `cwd`, not the repository you have in mind.** `--setting-sources
project` means "read `.claude/` under the current working directory," using the CLI's own definition of
"project" — the process's `cwd` at invocation time — not "the repository this code conceptually
belongs to." The moment a launcher runs the process from a per-story git worktree, a container mount,
or a CI checkout step whose `cwd` isn't the repo root, this silently diverges and an entire settings
layer, including the harness's own permission rules, goes unloaded with no error. One-line answer:
**read "project" as "whatever `.claude/` sits under `cwd` right now"; use `--settings <absolute path>`
when the launcher's `cwd` is not guaranteed to be the repository root.**

**`${CLAUDE_PLUGIN_ROOT}` is not the repository.** It resolves to the plugin's own installed directory
— typically somewhere under `~/.claude/plugins/cache/...` — never to the checkout of the repository the
plugin happens to be operating on. A hook that walks relative to `${CLAUDE_PLUGIN_ROOT}` or to its own
script path (`$0`) to find "the repo root" runs with no error and silently reads or writes the wrong
tree the moment the hook is converted from a project-local script into a plugin, because every path in
that walk still resolves to *something* — just not the checkout anyone meant. One-line answer: **use
`git rev-parse --show-toplevel` to find the repository root from inside a hook, never a path computed
relative to `${CLAUDE_PLUGIN_ROOT}` or `$0`.**

## Self-test

1. Why does writing "ENFORCE ALWAYS" in `CLAUDE.md` not actually enforce anything?
<details><summary>Answer</summary>Rules are enforced by the harness, not the model. A `CLAUDE.md` line shapes what the model tries to do inside its own turn, but nothing checks the tool call itself against that line — the model can genuinely try to follow it and still fail under context pressure, after a compaction, or against a conflicting nested rule. Only a `PreToolUse`/`PostToolUse` hook, a `permissions.deny` rule, or the sandbox evaluate the call itself, outside the model's own reasoning, which is what makes them guarantees rather than requests.</details>

2. An engineer writes `deny: ["Bash(aws *)"]` then `allow: ["Bash(aws s3 ls)"]` expecting the allow to carve out an exception. What actually happens, and why?
<details><summary>Answer</summary>`aws s3 ls` is still refused. `deny` is pooled across every settings layer and checked first, unconditionally; once a `deny` rule matches, `allow` is never reached regardless of restart or file order. There is no negation operator in the rule syntax, so the only fix is to narrow the `deny` rule itself — enumerate the dangerous subcommands (`Bash(aws s3 rm *)`, `Bash(aws ec2 terminate-instances *)`) and leave the safe one unmatched by any deny rule.</details>

3. A skill ships `allowed-tools: [Read]`. Does that skill's invocation get blocked from calling `Bash`?
<details><summary>Answer</summary>No. `allowed-tools` pre-approves the listed tools — it skips the permission prompt for `Read` — but does nothing to the rest of the tool set, which stays exactly as available as the session's broader permissions already made it. The same skill can still call `Bash(rm -rf build/)` unopposed. A real ceiling requires `disallowed-tools` in the frontmatter, or a `permissions.deny` rule in project settings for a guarantee that holds even against a hostile skill body.</details>

4. Why did `--setting-sources project` silently drop the harness's own permission rules when the coder ran inside a per-story git worktree?
<details><summary>Answer</summary>`--setting-sources project` reads `.claude/` under the process's `cwd` at invocation time, using the CLI's own definition of "project" — not the repository the engineer conceptually means. The worktree's `cwd` was not the harness repo root, so `<cwd>/.claude/settings.json` did not exist there; the whole settings layer carrying `permissions.allow`/`deny` silently failed to load. The symptom looked exactly like a rule typo (some commands refused, others allowed) because the bare `acceptEdits` defaults still worked. The fix is `--settings <absolute path>`, which resolves independently of `cwd`.</details>

5. State the trailing-newline incident and the general law it produced.
<details><summary>Answer</summary>A footer-stripping regex ending `\s*$`, applied across a batch to trim trailing whitespace before certifying files clean, ate the trailing newline on nine files, because `\s` also matches `\n` and the greedy match at end-of-string consumed every trailing newline character. The certifier signed off on the regex's own output, never re-reading the file actually written to disk afterward. The law: certify from final state, never from a pre-write computation — hash or inspect the artefact after it is written and closed, not the buffer or in-memory value that produced it.</details>

6. How many hook events are there in v2.1.2xx, and which two does a stale "32" count miss?
<details><summary>Answer</summary>33. A count of 32 is missing `PreModelSwitch` and `PostModelSwitch`, a pair added to cover a model-switch lifecycle the earlier count predates.</details>

7. What is the current default subagent nesting depth, and what was it two releases earlier in the same v2.1.2xx line?
<details><summary>Answer</summary>The current default is 3, as of v2.1.219 and later. In v2.1.217 through v2.1.218 the default was 1 — a subagent could not spawn its own without the operator explicitly raising `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`.</details>

8. A reviewer says "the eval suite stayed green, so this plugin's rollout is complete." What is missing from that claim?
<details><summary>Answer</summary>A versioned plugin with hooks and an eval suite buys review, rollback, and measurement of the *capability itself* — it does not by itself buy review capacity for the *output volume* that capability enables. The governance incident this guide records found that months after a clean rollout, most agent-authored diffs were being approved by reviewers skimming for shape rather than reading for correctness, because diff volume had grown past what the review team could read closely — and nothing about the plugin's versioning or eval gate measured that.</details>

9. Why is "the md5 taken over a patched harness" and "the unpinned digest" the same incident rather than two separate ones in this guide?
<details><summary>Answer</summary>Both name §3.10.4's second incident: an MD5 was computed over an in-memory patched copy of the harness to certify "this is the exact code the eval ran against," but the patch was never written back to the on-disk files, which still failed to compile. §3.10.5 restates that same incident as the generalised law "pin the harness beside the digest" — it introduces no new incident narrative of its own, so counting it separately double-counts one event.</details>

10. What does `bypassPermissions` actually still refuse, now that the "it protects `.git` and `.claude`" belief is known to be stale?
<details><summary>Answer</summary>It allows protected-path writes outright — a prompt-injected instruction can rewrite `.claude/settings.json` or corrupt `.git`'s internals with no prompt in the way. What it still refuses is critical-path `rm`/`rmdir` deletions, explicit `ask`-rule matches, always-interactive tools (`AskUserQuestion`, `requiresUserInteraction` MCP tools), and two cross-session messaging safeguards (`isolatePeerMachines`, held inbound messages).</details>
