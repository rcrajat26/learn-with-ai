## How to use the trap index

A trap here is a wrong belief that survives reading the documentation — not a typo, not an edge case nobody would guess, but a plausible mental model that produces correct-looking code until the one input, load pattern, or JDK version that breaks it. Every row is one pitfall harvested from the 219-file note set, normalised into the same four columns.

Scan by reading only the **wrong belief** column top to bottom, one part at a time. Stop at any row where you cannot immediately produce the symptom and the fix from memory — that is a real gap, not a false alarm, because the wrong belief is written in the voice of someone who already half-believes it. Do not read the symptom or fix columns first; they will make the trap look more obvious than it is under interview pressure, where you get the wrong belief's premise and nothing else.

The honest warning this table cannot get around: being able to refute a trap in writing, with the source file open, is not the same skill as refuting it out loud, cold, in the ninety seconds an interviewer gives you before moving on. Use the table to find what you don't know; use spoken rehearsal — saying the fix out loud before checking it — to find what you know but cannot yet say fast enough.

|---|---|---|---|---|
| Redeclaring a field in a subclass "overrides" it, so the parent's own methods will see the child's value. | `WithdrawalTransaction`'s own `compareTo`, `toString`, and validation logic keep reading the parent slot nobody updates any more, so a card withdrawal reports `PENDING_VERIFICATION` to reconciliation forever while the client's screen shows `DEP-301 CAPTURED` — a silent divergence that survives every unit test touching only the subclass. | Never shadow a superclass field; make superclass fields `private`, expose a `protected` accessor, and override the accessor instead. | 1.15.12 | [inheritance-and-dispatch/01-basics.md](inheritance-and-dispatch/01-basics.md) |
| Subclassing is safe as long as you only *add* methods and never override anything. | A future superclass release adds a method with the same signature as your added method but a different contract — your `isFrozen()` meaning "restriction present" silently becomes an override of the library's new `isFrozen()` meaning "row locked for a payment run," and the library's own internals act on the wrong answer. | Favor composition over inheritance when a superclass's own internal self-use isn't documented as API; a new superclass method never becomes part of a composed class's surface. | 1.15.15 | [inheritance-and-dispatch/01-basics.md](inheritance-and-dispatch/01-basics.md) |
| A `final` field is safe to read from anything a constructor triggers, because "final fields are initialised before the constructor returns." | `WithdrawalTransaction`'s constructor calls `expectedSettlement()`, `CardWithdrawal` overrides it as `return psp.timeout();`, and `psp` is still `null` — a NullPointerException, or worse, a silently-wrong default like an unlimited `Money` limit — because the field is only initialised before *that class's own* constructor returns, which is after any override the superclass constructor called. | Have constructors call only `private`, `static`, or `final` methods; do work needing a fully-built object in a static factory instead. | 1.15.14 | [inheritance-and-dispatch/01-basics.md](inheritance-and-dispatch/01-basics.md) |
| A method with the right name and a plausible parameter type overrides the superclass method. | `boolean equals(CardWithdrawal other)` doesn't override `boolean equals(Object)` — it's a silent overload, so `HashSet.contains`/`List.remove` keep calling the inherited identity `equals` and withdrawal deduplication silently stops working, investigated for an hour as "my override is not being called." | Put `@Override` on every method intended to override or implement, without exception, and configure the build to treat the `overrides` lint category as an error. | 1.15.17 | [inheritance-and-dispatch/01-basics.md](inheritance-and-dispatch/01-basics.md) |
| A `null` argument at an ambiguous overload call site is a runtime `NullPointerException` waiting to happen. | A developer wraps the call in a null guard, or "fixes" the ambiguity by deleting an overload and silently changing which method every other call site resolves to — when in fact `null` selection is a purely compile-time decision that either resolves or fails the build. | Cast at the call site to disambiguate; never change the overload set to work around an ambiguity error. | 1.15.8 | [inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md](inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md) |
| The class named in a `Methodref`'s comment in a stack trace or `javap` listing is the class whose body actually ran. | Chasing a bug in the wrong file — typically an abstract class or interface with no body at all — because the `Methodref` names the *static type at the call site*, not the receiver's runtime class that `invokevirtual`/`invokeinterface` actually dispatched to. | Read the stack trace's frames, which name runtime classes, instead of inferring the executed class from the call site's descriptor. | 1.15.9 | [inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md](inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md) |
| Reaching for `final` on a class or method makes a hot call faster. | A diff full of `final` keywords lands with a benchmark that doesn't move, because a monomorphic call site is already devirtualised by HotSpot's profile-guided speculation, and a megamorphic site stays megamorphic regardless of `final`. | Reduce the receiver population at the hot bytecode index if speed matters; use `final` for the correctness/API-evolution property (forbidding subclassing), not as an optimisation. | 1.15.11 | [inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md](inheritance-and-dispatch/01a-overload-resolution-and-dispatch.md) |
| `default` methods let an interface carry per-instance state, faked with a `static` map keyed by `this`. | The map is a global that is never cleared, so every adapter instance that should be garbage stays strongly reachable from the interface's static field — a slow leak that only shows under the 55k-peak session load. | Use an abstract class, or delegate to a collaborator object supplied through an abstract accessor, if the behaviour genuinely needs state. | 1.16.3 | [inheritance-and-dispatch/01b-interfaces.md](inheritance-and-dispatch/01b-interfaces.md) |
| A green build proves an interface change is safe. | `AbstractMethodError` appears in production days later, on a module whose jar was not rebuilt because nothing in its own source changed — adding an `abstract` method to a published interface is binary-incompatible even though it compiles cleanly against source that already implements it. | Treat any added `abstract` method on a published interface as a major version bump; use a `default` with a real fallback, or one that throws with a clear message, when recompilation of every implementor can't be guaranteed. | 1.16.12 | [inheritance-and-dispatch/01b-interfaces.md](inheritance-and-dispatch/01b-interfaces.md) |
| A constant interface (fields only, implicitly `public static final`) is the idiomatic way to share constants, because it's concise. | `PaymentService implements LedgerConstants` advertises `SUSPENSE_POSITION` in its own public API, an `instanceof LedgerConstants` check becomes meaningful-looking nonsense, and the constants can't be removed without breaking dependents that never asked to inherit them. | Use a `final` class with a private constructor and `static final` fields (imported statically for short names), or an `enum` for a closed set. | 1.16.10 | [inheritance-and-dispatch/01b-interfaces.md](inheritance-and-dispatch/01b-interfaces.md) |
| Double-brace initialisation is a concise literal syntax with no cost. | A `NotSerializableException`-shaped failure at a cache boundary, or an old-gen leak where the retained root is a supposedly-"constant" collection — because the anonymous subclass created by double-brace init holds a strong synthetic reference to its enclosing instance. | Use `Set.of`/`Map.of`/`List.of`, or a static factory method that builds and returns a plain collection. | 1.17.8 | [inheritance-and-dispatch/02-nested-classes.md](inheritance-and-dispatch/02-nested-classes.md) |

### Part 1 — enums (§1.18)

| The wrong belief | The symptom in production | The fix | Leaf | Where |
|---|---|---|---|---|
| An enum "is just constants," so its constructor is cheap and its initialization is inert. | A startup or first-request latency spike whose stack trace bottoms out at an innocuous field read — or an `ExceptionInInitializerError` on first touch followed by `NoClassDefFoundError` on every later touch — because the first `getstatic` of any constant runs every constructor, and one calling `Currency.getInstance(code)` or registering into a static map moved real work there. | Keep enum constructors to plain field assignment; put anything that can fail or block behind a lazily-initialised holder class. | 1.18.1 | [enums/01-basics.md](enums/01-basics.md) |
| `getClass()` on any enum constant returns the enum's own class. | `isEnum()` returns `false` on the result for a constant with a per-constant body, because that constant's `getClass()` returns a synthetic anonymous subclass (`RestrictionSource$1`), not `RestrictionSource`. | Use `Enum.getDeclaringClass()`, not `getClass()`, when the enum type itself is needed. | 1.18.5 | [enums/01-basics.md](enums/01-basics.md) |
| Enum constants being singletons licenses hanging mutable state off them. | A slow heap climb attributed vaguely to "the enum," plus cross-test pollution, because a `private final Map<...> attempts = new ConcurrentHashMap<>()` field on a constant is process-lifetime global mutable state with no eviction and no ownership. | Give enum constants only `final` per-constant configuration; put anything with a lifecycle in an injected bean with a deliberately chosen scope. | 1.18.2 | [enums/01-basics.md](enums/01-basics.md) |
| Overriding `toString()` on an enum means `valueOf` can round-trip that string back to the constant. | Parsing the overridden `toString()` output back through `valueOf` throws `IllegalArgumentException`, because `valueOf` matches only the declared constant name, never the overridden `toString()`. | Keep a separate name-keyed lookup (or use `name()`) for round-tripping; treat `toString()` as display-only. | 1.18.6 | [enums/01a-implicit-members-and-identity.md](enums/01a-implicit-members-and-identity.md) |
| `EnumSet.allOf(RestrictionType.class)` is just another `values()` call in disguise. | Code assuming it copies `values()`' allocation behavior misreads the cost — `EnumSet` internally uses a shared, cached constants array (`getEnumConstantsShared`) rather than allocating a fresh array per call. | Understand `EnumSet.allOf` as reading a shared cached array, distinct from `values()`'s fresh-array-per-call cost. | 1.18.7 | [enums/01a-implicit-members-and-identity.md](enums/01a-implicit-members-and-identity.md) |
| Persisting `ordinal()` is only dangerous when it lands in a database. | A `Map<Integer,X>` keyed by `ordinal()` cached in Redis, a protobuf/Avro field, a Kafka message, or a bare `@Enumerated` (whose default is `ORDINAL`) all decode correctly until the enum is edited, then silently decode to a *different valid value* — the worst failure mode, because nothing alerts. | Restrict ordinal use to inside a single JVM run (`EnumSet`, `EnumMap`, a local array cache); persist `name()` or an explicit code field instead. | 1.18.8 | [enums/01a-implicit-members-and-identity.md](enums/01a-implicit-members-and-identity.md) |
| `catch (IllegalArgumentException e)` around `valueOf` is the standard tolerant parse for unknown or null input. | Every unknown value pays a full stack-trace fill on the exception path, and a `null` input is missed entirely because `valueOf(null)` throws `NullPointerException`, not `IllegalArgumentException`. | Build an explicit name-keyed lookup `Map` that returns an `Optional` or a sentinel, handling `null` before the lookup. | 1.18.9 | [enums/01a-implicit-members-and-identity.md](enums/01a-implicit-members-and-identity.md) |
| Enum hashing is stable because the constants themselves are stable. | A cache key built by concatenating `hashCode()` values misses on every restart, or a shard computed as `type.hashCode() % partitions` reassigns every deploy and silently reroutes traffic — because `Enum.hashCode()` is `final` identity-derived (`System.identityHashCode`), not content-derived. | Never let `Enum.hashCode()` cross a JVM-run boundary; use `EnumMap`/`EnumSet` for declaration order or `name()`/an explicit code for a stable key. | 1.18.10 | [enums/01a-implicit-members-and-identity.md](enums/01a-implicit-members-and-identity.md) |
| `EnumSet.copyOf(Collection)` is safe on any collection, including an empty one. | `EnumSet.copyOf(new ArrayList<RestrictionType>())` throws `IllegalArgumentException: Collection is empty` when the source isn't itself an `EnumSet`, because the empty-non-`EnumSet` case can't infer the element type. | Guard the empty case, or pass a non-empty collection / an `EnumSet` source. | 1.18.11 | [enums/01b-collections-patterns-and-guarantees.md](enums/01b-collections-patterns-and-guarantees.md) |
| A `default` branch in an enum `switch` that returns a plausible fallback is a safe way to handle "anything else." | `default -> Queue.COMPLIANCE;` quietly absorbs every newly added enum constant into "compliance can triage anything," masking the fact that the new constant was never actually considered. | Omit `default` and let the compiler force an explicit case for every new constant, or fail loudly on the unhandled case. | 1.18.12 | [enums/01b-collections-patterns-and-guarantees.md](enums/01b-collections-patterns-and-guarantees.md) |
| An enum constant with a per-constant body can safely fetch its own dependencies through a static holder. | The constant's behavior becomes coupled to global static state resolved at class-init time, reintroducing the same static-dependency and testability problems a strategy object was meant to avoid. | Inject dependencies into the enum constant's method call, or move the logic to an injected strategy object rather than a static holder lookup. | 1.18.13 | [enums/01b-collections-patterns-and-guarantees.md](enums/01b-collections-patterns-and-guarantees.md) |
| A lookup map built from a `private static final Map` field initialiser that calls a static method declared later in the same class is safe because "it's all one class." | It compiles, then throws at class initialisation, because the field initialiser runs in textual order and calls the later-declared static method before that method's own dependencies (or the enum's own constant list) are ready. | Order static declarations so a lookup-building method never runs before what it depends on is initialised; build the map lazily via a holder class if ordering is fragile. | 1.18.14 | [enums/01c-production-patterns-and-guarantees.md](enums/01c-production-patterns-and-guarantees.md) |
| The typesafe-enum pattern (pre-Java-5) is purely historical and not worth knowing. | An enum gets contorted to fit an open set — usually with an `OTHER` constant carrying a string payload — reintroducing every problem the enum was meant to solve, because a real enum's constant set is closed at compile time. | Recognise the open-set case (extensible by a downstream module, or instances computed rather than declared) and write the typesafe-enum class directly, as `java.util.Currency` and `java.time.ZoneId` do. | 1.18.17 | [enums/01c-production-patterns-and-guarantees.md](enums/01c-production-patterns-and-guarantees.md) |

|---|---|---|---|---|
| Declaring `throws Exception` is a fine way to make a checked-exception compile error go away. | A caller of a method declared `throws Exception` cannot distinguish "this can throw `SQLException`" from "this can throw `InterruptedException`" without reading the implementation — it defeats catch-or-declare's purpose. | Declare the specific checked exception, or translate it to an unchecked exception at the boundary. | 1.20.3 | [exceptions/01-basics.md](exceptions/01-basics.md) |

| Precise rethrow is a property of the `throw e` statement in isolation. | Adding an unrelated reassignment of `e` — for what looks like a harmless logging tweak — breaks compilation at a `throw` statement several lines below, even though the reassignment never executes before that `throw`. | Treat precise rethrow as whole-clause analysis: keep the catch parameter effectively final for the entire clause, not just up to the `throw`. | 1.20.11 | [exceptions/01b-catch-multicatch-and-precise-rethrow.md](exceptions/01b-catch-multicatch-and-precise-rethrow.md) |

### Part 1 — generics (§1.21)

| The wrong belief | The symptom in production | The fix | Leaf | Where |

## The ten traps that decide interviews

| The wrong belief | Why it is the one that gets asked |
|---|---|
| `private` methods compile to `invokespecial` — repeated by essentially every pre-2018 blog post and interview answer key. | It is the single most reliable way to separate a candidate who read a 2015 blog post from one who has run `javap` on a JDK 11+ build; the JEP 181 boundary is exact and checkable in seconds. |
| `==` on `Integer` compares values, except for some edge case above 127. | Every candidate has seen `-128..127` quoted; almost none can say why the boundary exists (`AutoBoxCacheMax`, `IntegerCache`) or that it is `Integer`-only, which is exactly where the follow-up question goes. |
| `==` on strings is a reliable equality check because it works in the unit tests, which use literals. | It is the fastest way to test whether a candidate actually understands string interning versus just having memorised "always use equals." |
| A plain `try { return x; } finally { return y; }` with no exceptions anywhere is safer than the throw-then-return case, because "nothing is being caught." | It exposes whether a candidate understands abrupt completion as a JLS concept or only knows "don't put return in finally" as a rule of thumb with no mechanism behind it. |
| Declaring `equals(RestrictionKey other)` alongside `Object.equals(Object)` overrides equality for that type. | It is the textbook overload-versus-override trap, and it produces a live demonstration on the whiteboard: write the code, ask what a `HashSet` does with it, and watch the candidate's model break in real time. |
| `BigDecimal.equals` means "same amount of money," the way `Integer.equals` means "same number." | Every candidate who has touched financial code has hit this once; whether they can state the `compareTo`-versus-`equals` distinction precisely, unprompted, is a strong signal. |
| A `HashMap`/`HashSet` key type is safe as long as developers "remember not to mutate" any field that feeds `hashCode()`. | It tests whether a candidate reasons about correctness structurally (make the bug impossible) or procedurally (trust the team to remember), which is a staff-level distinction dressed as a trivia question. |
| `final` fields on a lazily-initialised singleton rescue the non-`volatile` double-checked-locking form. | It is the cleanest way to find out whether a candidate actually understands the JMM's `final`-field freeze or is pattern-matching "final means safe" onto a case where the freeze's antecedent isn't satisfied. |
| Increasing `-Xss` fixes unbounded recursion. | It separates candidates who treat a stack trace as a number to tune away from candidates who ask what the recursion depth is actually a function of. |
| A record's generated `hashCode()` value is as stable a contract as `String.hashCode()`'s specified polynomial. | It is the modern-Java version of the same lesson tested three different ways above, and it catches candidates who know records are "value types" without knowing the JLS explicitly leaves the hash algorithm unspecified. |
