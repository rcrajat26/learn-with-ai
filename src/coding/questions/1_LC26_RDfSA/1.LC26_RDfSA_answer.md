### 3.2 The invariant and the write-safety proof are absent

Your code writes to `nums[s+1]` while still reading `nums[c]` and `nums[c-1]`.
Nothing in the attempt establishes that the write cannot destroy a cell you have
yet to read. It is safe — I verified it, and here is the proof you owe, in the
form your code needs (note it is *subtly different* from the version in
`_evaluation1.md § 3.5`, because you changed the comparison to `nums[c-1]`):

> Let `d(i)` be the number of distinct values in the **original** `nums[0..i]`.
> Before each iteration, `s = d(c-1) - 1`. Since `d(c-1) <= c`, we have
> `s + 1 <= c`.
>
> After iteration `c`'s write, all future reads are at indices `>= c` (the next
> iteration reads `nums[c+1]` and `nums[c]`). So:
> - If `s + 1 < c`, the write target is strictly below every future read. Safe.
> - If `s + 1 == c`, the statement is `nums[c] = nums[c]` — a self-write that
>   changes nothing. Safe.
>
> Therefore `nums[c-1]` always holds its **original** value when read, and no
> unread datum is ever lost.

That second bullet is not a formality. The equality case is live: it occurs on
every all-distinct input, which is when `s+1 == c` for the entire loop. And the
first case genuinely overwrites live-looking data — trace `[0,0,1,...]`: at
`c = 2` you write `nums[1] = 1`, destroying the original `0` at index 1. That is
fine only because index 1 is never read again. **You have to know that.**

## 4. The correct answer

### 4.1 Brute force A — collect distinct into a list, copy back

```java
int removeDuplicatesBrute(int[] nums) {
    List<Integer> unique = new ArrayList<>();
    for (int value : nums) {
        if (unique.isEmpty() || unique.get(unique.size() - 1) != value) {
            unique.add(value);
        }
    }
    for (int i = 0; i < unique.size(); i++) {
        nums[i] = unique.get(i);
    }
    return unique.size();
}
```

**Time** Θ(n) — two passes, amortised O(1) per append.
**Space** Θ(k) auxiliary, degenerating to Θ(n) on all-distinct input.
**Why it fails here:** violates the O(1)-space contract, which is the entire
point of the problem. Also boxes every element: ~3·10⁴ `Integer` allocations plus
an unboxing on each comparison.

**Java trap worth naming aloud.** Line 4's `!=` compares *ints*, because the
right operand is an `int` and the left is unboxed to match. Had both sides been
`Integer`, `!=` would compare **references**, and the code would work only for
values in `[-128, 127]` (the `Integer` cache) and break silently outside it. Here
the constraint `-100 <= nums[i] <= 100` sits entirely inside the cache — so the
buggy version would pass every test case in this problem and fail in production.
That is a genuinely nasty interaction between a constraint and a language
footgun.

### 4.2 Brute force B — shift-left on each duplicate

```java
int removeDuplicatesShift(int[] nums) {
    int n = nums.length;
    int i = 1;
    while (i < n) {
        if (nums[i] == nums[i - 1]) {
            System.arraycopy(nums, i + 1, nums, i, n - i - 1);   // O(n) per removal
            n--;
        } else {
            i++;
        }
    }
    return n;
}
```

**Time** O(n²). **Space** Θ(1) — genuinely in-place.
**The input that kills it:** `n = 3·10⁴` all equal. That is ~3·10⁴ removals, each
shifting ~3·10⁴ elements ≈ **9·10⁸ element moves**. Too slow in Java.

This is the trap the word "remove" sets, and it is the most common first instinct.
Naming it and rejecting it *with the arithmetic* is worth real credit — it shows
you read `n <= 3 * 10^4` as a signal rather than decoration.

### 4.3 Optimal — canonical form (count convention)

This is the version I would write in an interview. Note the cursor convention:
`write` is **a count**, which is simultaneously **the index of the next free
slot**. That is what makes `return write;` need no arithmetic.

```java
class Solution {

    /**
     * Collapses runs of equal values in a non-decreasing array, in place.
     *
     * @param nums sorted non-decreasing; length >= 1 per the constraints
     * @return k, the number of distinct values, now occupying nums[0..k-1]
     */
    public int removeDuplicates(int[] nums) {
        // Convention: `write` counts elements already decided, and is therefore
        // also the index of the next free slot. nums[0] is always the first
        // element of the first run, so it is kept unconditionally.
        int write = 1;

        // Invariant, true before every iteration:
        //   (1) nums[0 .. write-1] == the distinct values of the ORIGINAL
        //       nums[0 .. read-1], in ascending order; and
        //   (2) 1 <= write <= read <= nums.length.
        // Clause (2) is the safety property: the write cursor never passes the
        // read cursor, so no unread element is ever destroyed.
        for (int read = 1; read < nums.length; read++) {
            if (nums[read] != nums[write - 1]) {   // differs from the last value KEPT
                nums[write++] = nums[read];
            }
        }

        // read == nums.length, so clause (1) covers the whole array: write == k.
        return write;
    }
}
```

**Why `nums[write - 1]` and not `nums[read - 1]`.** Both are correct (§ 5 rows 1
and 2). `nums[write-1]` means *"is this different from the last value I decided to
keep?"* — a direct restatement of invariant clause (1), provable in one sentence.
`nums[read-1]` means *"is this different from the original previous element?"*,
which is correct only after a case analysis showing that cell wasn't clobbered
(§ 3.2). Prefer the formulation whose correctness argument is one sentence. And
decisively: only `nums[write-1]` generalises — see § 4.7.

### 4.4 Optimal — your form (index convention), annotated

Your code is equally correct. Here it is with what was missing:

```java
class Solution {
    public int removeDuplicates(int[] nums) {
        if (nums.length == 0) return 0;   // unreachable given 1 <= nums.length;
                                          // kept only because `return s+1` mishandles n == 0
        // `s` is an INDEX: the last filled slot of the deduplicated prefix.
        // Under this convention k == s + 1, hence the adjustment on return.
        int s = 0;

        // Invariant before each iteration: s == d(c-1) - 1, where d(i) counts
        // distinct values in the ORIGINAL nums[0..i]. Since d(c-1) <= c, we get
        // s + 1 <= c, so the write below is always to a consumed cell or is a
        // self-write. See the proof in section 3.2.
        for (int c = 1; c < nums.length; c++) {
            if (nums[c] > nums[c - 1]) {       // '>' == '!=' under non-decreasing order
                nums[s + 1] = nums[c];
                s++;
            }
        }
        return s + 1;
    }
}
```

The `length == 1` guard is deleted — the loop handles it (§ 3.1). Both
conventions are defensible; the count convention has one fewer place to make a
mistake, which is why it is the one to standardise on.

### 4.6 Complexity derivation

**Time — Θ(n).** The loop variable starts at 1, increases by exactly 1 per
iteration, is never reset or modified in the body, and the loop exits at `n`.
So the body runs exactly `n - 1` times. Each body is: one array read
(`nums[read]`), one array read of the comparand, one comparison, and at most one
array store plus one increment — all Θ(1). Total `(n-1)·Θ(1) + Θ(1) = Θ(n)`.

Finer accounting, in case an interviewer pushes:
- **Comparisons:** exactly `n - 1`.
- **Array reads:** exactly `2(n - 1)`. Cacheable — hoist the last kept value into
  a local `int last`, and you halve it to `n - 1` reads plus register access.
- **Stores:** exactly `k - 1` if you guard with `if (write != read)`; otherwise up
  to `n - 1`, most of them self-writes on nearly-distinct input. Only worth doing
  if writes are expensive (flash, write-amplified media, dirty-page tracking).
  On commodity hardware the extra branch costs about what the store saves — I
  would mention it and not ship it.

**Space — Θ(1).** Two `int` locals = 8 bytes, independent of `n`. No array, no
collection, no autoboxing, no recursion (so no stack growth). The input mutation
is required by the contract, not counted as auxiliary.

### 4.7 The extension you skipped — "at most twice"

> Each distinct value may appear **at most twice**. `[0,0,1,1,1,2,2,3,3]` →
> `k = 7`, prefix `[0,0,1,1,2,3,3]`. (This is LC 80.)

**From the canonical form, this is a two-token change:**

```java
public int removeDuplicatesTwice(int[] nums) {
    int write = 0;
    for (int read = 0; read < nums.length; read++) {
        // Keep nums[read] unless we have already kept two copies of it.
        // nums[write-2] is the value two slots back in the KEPT prefix, so
        // this is exactly "have I already kept two of this value?"
        if (write < 2 || nums[read] != nums[write - 2]) {
            nums[write++] = nums[read];
        }
    }
    return write;
}
```

`write - 1` became `write - 2`; the seed became `write = 0` with a `write < 2`
bootstrap. The invariant generalises verbatim: *`nums[0..write-1]` holds each
distinct value of the scanned portion at most twice, in order, and
`write <= read`.* Set the constant to `m` and you have "at most `m` copies" for
free.

**Now try it from your form.** You compare against `nums[c-1]` — a property of
the **original** array. But the rule "at most twice" is a fact about **how many
copies you have already kept**, and the original array cannot tell you that. Two
inputs can have identical `nums[c-1]` relationships and require different
decisions at index `c` depending on how many copies the output already holds.
The most common patch is to look two back in the original:

```java
// WRONG
if (nums[c] > nums[c - 2]) { nums[s + 1] = nums[c]; s++; }
```

Killer input: `[1,1,1,1]`. Expected `k = 2`, prefix `[1,1]`. Here `nums[c]` is
never greater than `nums[c-2]`, so nothing is ever kept beyond the seed, and you
cannot even express "keep the second copy" — the comparison has no access to the
count of copies retained. The approach doesn't need patching; it needs replacing
with the write-relative comparison.

**This is the entire point of the choice Hint 3 asked you to make deliberately.**
Comparing against the *original neighbour* solves this one problem. Comparing
against *what you kept* solves the whole family, because the keep-predicate then
reads the output — which is what a filter actually needs. Ninety seconds on the
extension would have taught you that; skipping it means pass 2 bought you a
solved instance instead of a pattern.

### 5.1 The galloping solution (worth knowing)

Instead of examining every element, jump over each run of duplicates with an
exponential probe followed by a binary search.

```java
public int removeDuplicatesGalloping(int[] nums) {
    int write = 0;
    int read = 0;
    while (read < nums.length) {
        nums[write++] = nums[read];          // write <= read still holds
        read = endOfRun(nums, read);         // skip the whole run in O(log runLength)
    }
    return write;
}

/** First index after `start` whose value differs from nums[start]; nums.length if none. */
private static int endOfRun(int[] a, int start) {
    final int n = a.length;
    final int target = a[start];
    int lo = start + 1;      // invariant: a[i] == target for all i in [start, lo)
    int step = 1;
    while (lo < n && a[lo] == target) {
        int probe = Math.min(lo + step, n);
        if (probe < n && a[probe] == target) {
            lo = probe + 1;
            step <<= 1;
        } else {
            int hi = probe;                  // a[hi] != target, or hi == n
            while (lo + 1 < hi) {            // narrow to adjacent
                int mid = lo + (hi - lo) / 2;
                if (a[mid] == target) lo = mid; else hi = mid;
            }
            return hi;
        }
    }
    return lo;
}
```

`write <= read` still holds, so it is still in-place and safe. Verified on
`[3,3,3,5]` → 2, `[3,3,3,3]` → 1, `[1,2]` → 2, `[0,0,1,1,1,2,2,3,3,4]` → 5.

**Honest caveats.** Far more code and far more bug surface than eight lines; the
constant factor and the branch mispredictions from binary search mean that at
`n = 3·10⁴` the flat linear scan is probably *faster in wall-clock terms* despite
doing 20× more comparisons, because it is perfectly predictable and
cache-sequential. Ship #1. But knowing #5 exists is what lets you answer § 6
correctly, and mentioning it after delivering #1 is a strong close.

## 6. Why the optimal is optimal

**A correction, because it changes the answer.** My pass-0 `_reasoning.md § 7`
and pass-1 `_evaluation1.md § 4` both claimed Ω(n) is a lower bound, on the
grounds that "any correct algorithm must inspect every element, since an
unexamined element could be a distinct value." **That argument is wrong**, and
§ 5.1 is the counterexample: on `[3,3,3,…,3]` the galloping solution returns the
right answer after O(log n) probes, having never looked at most of the array.
Sortedness lets you skip. Treat the Ω(n) claim in those two files as retracted.

**The correct picture.**

*Lower bound.* Any algorithm must write `k` output elements, so Ω(k) is trivial.
The real bound is on comparisons. Suppose the algorithm has probed positions `i`
and `j` with `i < j` and found `a[i] < a[j]`. If it has not examined every
position between them, an adversary is free to place a **third distinct value**
in the unexamined gap — consistent with sortedness and with every probe made so
far — changing the correct answer. So to rule out a hidden run between two probes
of differing value, the algorithm must narrow that gap to adjacent indices, which
costs Ω(log gap) probes. Summing over the `k-1` boundaries and applying Jensen's
inequality to the worst-case distribution of gap sizes gives
**Ω(k log(n/k))** comparisons.

*Upper bound.* § 5.1 achieves O(k log(n/k)). So the galloping algorithm is
**asymptotically optimal**, matching the lower bound.

*Where that leaves the two-pointer scan.* When `k = Θ(n)` (few duplicates),
`k log(n/k) = Θ(n)` and the linear scan is optimal outright. When `k << n` it is
asymptotically suboptimal — provably beatable. It remains the right answer to
give in an interview because:

1. It is optimal in the **single-pass / streaming model**, where you get each
   element once, in order, and cannot seek. That is the realistic model for most
   places this pattern actually appears.
2. It is Θ(1) space, minimal-branch, cache-sequential, and eight lines — so it
   wins on wall-clock at this problem's `n` regardless of the comparison count.
3. Θ(n) is optimal in **writes** up to a constant, and exactly `k-1` with the § 5
   row-4 guard.

So: **not proven optimal in the comparison model — and in fact beatable there.
Proven optimal in the streaming model, and the best practical choice at this
input size.** That is the honest three-clause answer, and volunteering the
distinction unprompted is a strong Staff-level signal. It is also a good lesson in
not repeating a lower-bound claim just because it sounds obvious — I did exactly
that in pass 0.

## 7. Interview delivery script

Verbatim, roughly 75 seconds before writing code.

> **Clarify.** "The array is sorted, so duplicates are adjacent — that's the
> lever the whole problem turns on. Three things I want to confirm. First, can I
> leave arbitrary garbage beyond index `k-1`? The underscores in the examples
> suggest yes, and that permission is what lets me overwrite rather than shift.
> Second, by in-place do you mean strict O(1) auxiliary space — so no second
> array even if I copy it back? Third, I see `1 <= nums.length`, so I can assume
> non-empty; tell me if you'd rather I handle zero."
>
> **Brute force, priced.** "Two baselines. The easy one collects distinct values
> into a list and copies them back: O(n) time but O(k) extra space, so it fails
> the in-place requirement. The more tempting wrong one is to read 'remove' as
> 'delete and shift left,' which is O(n²) — all-equal input at n = 30,000 is
> about 9·10⁸ element moves. Too slow. So I need to remove without shifting."
>
> **Bottleneck.** "The list is the only thing costing me space, and it's
> redundant: after processing the first `i` elements it holds at most `i` entries.
> The output is never longer than the input I've already consumed — so the output
> can live in the input array's own prefix."
>
> **Optimal.** "Two pointers. `write` is the count of elements I've decided,
> which is also the index of the next free slot — I'll pick that convention
> deliberately, because it means the answer needs no `+1` at the end. `read`
> scans. Seed `write = 1`, since `nums[0]` is always the first element of the
> first run; that also removes the `write-1 == -1` boundary case. For each
> `read`, compare `nums[read]` against `nums[write-1]` — the last value I
> actually kept. If it differs, it starts a new run, so store it and advance
> `write`.
>
> The invariant is: `nums[0..write-1]` holds exactly the distinct values of the
> original `nums[0..read-1]` in order, **and `write <= read`**. That second
> clause is the safety property — it's why I can never overwrite something I
> haven't read. When they're equal the store is a self-write and harmless; when
> `write < read` I'm writing into cells I've already consumed. At exit
> `read == n`, so the invariant says `write` is exactly `k`."
>
> **Complexity.** "Θ(n) time — exactly `n-1` iterations of constant work. Θ(1)
> space, two ints, no allocation and no boxing. Worth a caveat on optimality:
> Θ(n) is optimal in a streaming model, and optimal outright when `k` is
> proportional to `n`. But it's *not* an unconditional lower bound — because the
> array is sorted, you can gallop over each run with exponential-plus-binary
> search and get O(k log(n/k)), which beats linear when there are few distinct
> values. Here `k` is capped at 201 by the value range, so that's about 1,500
> comparisons versus 30,000. I'd still ship the linear scan — it's eight lines,
> branch-predictable, and cache-sequential, so it's faster in wall-clock at this
> size — but the galloping version is the asymptotically optimal one."
>
> **Test.** "`[0,0,1,1,1,2,2,3,3,4]` → returns 5, prefix `[0,1,2,3,4]`, tail left
> as debris. `[7]` → loop doesn't run, returns 1. `[3,3,3]` → `write` never
> advances, returns 1. `[1,2,3,4]` → every store is a self-write, returns 4.
> `[-100,-100,-1]` → returns 2; note I use no sentinel value, the seed is a real
> element, so negatives are fine. And one limitation: if the input weren't
> actually sorted, this returns a wrong answer silently rather than throwing."
>
> **Volunteer the extension.** "The natural follow-up is 'allow each value at
> most twice.' Same skeleton — compare against `nums[write-2]` instead of
> `nums[write-1]`, with a `write < 2` bootstrap. Worth noting *why* that works:
> because I compared against what I'd **kept** rather than against the original
> previous element. The original-neighbour version solves this problem but can't
> express 'at most twice' at all, since the input can't tell you how many copies
> you've already emitted."

That last paragraph is the single highest-value thing in the script. It converts
"I solved your problem" into "I understand the family," and it costs fifteen
seconds.
