## 2. What you got right

Specific things you landed, not encouragement:

1. **You read "in-place" as a space bound, not a phrasing quirk.** Line 1 —
   *"space comp must be O(1) I cant use another array"* — is the correct reading
   of the contract, and it is the constraint that rules out every easy solution.
   Many attempts allocate an `ArrayList`, copy back, and call it in-place.

2. **You exploited sortedness for a *local* duplicate test.** You never reached
   for a `HashSet`. Comparing an element against its immediate predecessor is
   correct precisely because sortedness forces duplicates into contiguous runs —
   and that is the observation the entire problem rests on.

3. **You discovered the write cursor.** `s` is a real second pointer: a
   destination index that advances only on a keep-decision, decoupled from the
   scan index. You arrived at it by working the problem (lines 3→5 show the
   derivation: "mark c as replaceable" → "but I'd have to track whether r is
   already replaced" → "increment r, then `a[r]=a[c]`"). That progression is the
   correct one and it is the insight of the problem.

4. **`arr[s+1] = arr[c]` writes forward instead of shifting.** The instinct that
   "remove" means "shift everything left on each duplicate" is the standard trap
   and it is O(n²) — all-equal input at n = 3·10⁴ costs roughly 9·10⁸ element
   moves. You never went there. Worth knowing you dodged it.

5. **The comparison direction is safe.** Using `>` rather than `!=` is fine here,
   because non-decreasing order makes `arr[c] > arr[c-1]` and `arr[c] != arr[c-1]`
   equivalent. I checked whether `>` could mask anything; it cannot, under the
   stated precondition.

## 3. What breaks

### 3.1 No return statement — the contract is not satisfied

```
int p=0,c=1,u=-1,s=0;
while(c<arr.length) { ... }
// <- nothing here. k is never produced.
```

The judge's first assertion is on `k`. Your prose says *"once c is beyond the
size of arr.length close code"* — you closed the loop but never closed the
contract.

**Why this is more than a typo.** The missing line forces a decision you have not
made: is `s` a *count* or an *index*? Your prose calls it an index — *"tracks
till what point the array is sorted"* — and your code uses it as one
(`arr[s+1]` is the next free slot, so `s` is the last filled slot). Under that
reading the answer is `s + 1`, **not `s`**. Trace `[1,1,2]`: the loop ends with
`s = 1`, and the correct answer is `2`. Trace `[3,3,3]`: `s = 0`, correct answer
`1`. Returning `s` would be wrong by exactly one on every single input, including
both provided examples. You have a 50% chance of guessing right in pass 2 unless
you pin down what `s` denotes first.

### 3.2 `if (s != -1)` is dead code — the branch can never be false

```
int s=0;              // s starts at 0
...
if (s != -1) { ... }  // s is only ever incremented, so s >= 0 always
s++;                  // never decremented anywhere
```

`s` is initialised to `0` and the only assignment to it in the entire program is
`s++`. It is therefore never negative, and `s != -1` is a tautology. The guard
does nothing on every input.

This is not merely redundant — it is a **fossil of an unresolved worry**. Line 3
of your prose says: *"but now we'll have to track whether the r index is already
replaced."* That is exactly the right question to ask (can I overwrite a cell I
still need to read?). You raised it, then wrote a guard that cannot fire, then
moved on. The worry was never actually discharged; it was papered over. See § 3.5.

### 3.3 `u` is declared and never used

`int u=-1` appears in the declaration list and nowhere else. Presumably `u` was
the variable the `!= -1` test was originally meant to interrogate. Dead state in
a 9-line program is a signal an interviewer will read.

### 3.4 `p` carries no information — this is not a two-pointer solution

This is the substantive reasoning gap, not a bug.

```
int p=0, c=1;
while (c < arr.length) {
    ... arr[c] > arr[p] ...
    c++; p++;          // both, unconditionally, every iteration
}
```

`p` starts at `c - 1` and is incremented in lockstep with `c` forever. Therefore
`p == c - 1` is an invariant that holds at every point in the program, and every
occurrence of `arr[p]` could be textually replaced by `arr[c-1]` with zero
behavioural change. `p` is a second variable holding a constant offset, not a
second pointer.

Why it matters: you *think* your pointers are `p` and `c`, and that `s` is
auxiliary bookkeeping ("an index s which tracks..."). It is the reverse. The two
pointers that do the work are **`c` (scan) and `s` (destination)** — those are
the two that move independently. `p` is noise. Until that inverts in your head,
you have solved this instance without acquiring the pattern, and the pattern is
what transfers to the next six problems in this family.

### 3.5 The safety of the overwrite is asserted, never argued

You write into `arr[s+1]` while still reading from `arr[c]` and `arr[c-1]`. Nothing
in your attempt establishes that the write cannot destroy a cell you have yet to
read. It happens to be safe, and here is the argument you owe:

Let `d(i)` = the number of distinct values in the *original* `arr[0..i]`. Your
loop maintains `s = d(c-1) - 1` before each iteration. Since `d(c-1) <= c`, we get
`s + 1 <= c`. So the write index never exceeds the scan index. When `s + 1 < c`
the target was already consumed; when `s + 1 == c` the statement degenerates to
`arr[c] = arr[c]`, which changes nothing. Hence no unread datum is ever lost.

That paragraph is the difference between "it passed" and "I know why it passes."
An interviewer will ask for it. Note also what the argument *depends on*: the
judge ignoring everything past `k-1`. You never stated that the suffix is free
garbage, which is the permission slip for the whole approach.

### Hint 2 — stronger

The observation that unlocks the cleanup, still no algorithm:

- `p` is initialised to `c - 1` and incremented in the same statement as `c`,
  unconditionally. So `p == c - 1` is true at every instant the program runs.
  A variable whose value is a fixed function of another variable is not carrying
  state. You have **one** scanning index, not two.
- The two things in your program that move at genuinely different rates are `c`
  and `s`. That is where the pattern lives. `s` is not bookkeeping *for* your
  pointers — `s` **is** the second pointer. Invert which two variables you think
  are the core of your solution and the shape of the standard form should appear.
- `s` starts at `0` and the only statement touching it is `s++`. Now re-read
  `if (s != -1)`. Evaluate that condition on the first iteration, and on the
  last. What is it?
- The index-versus-count ambiguity in `s` is your off-by-one. There is a
  well-known way to make this class of bug structurally impossible: choose the
  convention where the cursor means **"the number of elements decided so far,"**
  which is simultaneously **"the index of the next free slot."** Under that
  convention the value you return needs no adjustment at all. Your current
  convention is the other one, which is why you owe a `+1`. Pick one and write it
  in a comment before you write any code.

### Hint 3 — near-giveaway

Technique named, invariant shaped. No code, and no algorithm you don't already
have.

**Name:** this is the **two-pointer in-place compaction** pattern — also called
read/write or fast/slow pointers. It is the array-level form of a *stable filter*:
one index scans, one index marks where the next surviving element goes, and
survivors are copied forward over territory the scanner has already cleared.
The general family is `LC 27`, `LC 80`, `LC 283`, `LC 443`, and the JDK's own
`List.removeIf`.

**Shape of the invariant** — write this above your loop and make your code obey
it, rather than writing code and hoping:

> Before every iteration: the prefix `arr[0 .. write-1]` holds exactly the
> distinct values of the portion already scanned, in ascending order — **and the
> write cursor never passes the scan cursor.**

The second clause is the safety property; it is the formal version of the worry
you raised on line 3 and never settled, and it is what licenses overwriting.
Prove it for your own `s` (the § 3.5 argument shows it holds — reconstruct it
yourself rather than copying it, and check the `[1,2,3,4]` boundary where the two
cursors coincide).

The first clause is what makes the return value fall out for free: at loop exit
the scanned portion is the whole array, so the cursor **is** `k`. If your return
statement needs arithmetic, your cursor convention is fighting your invariant —
that is the § 3.1 off-by-one telling you something structural, not a nuisance to
patch.

**One deliberate choice to make, not guess:** you compare against
`arr[c-1]` — the previous element of the *original* array. There is a second
option: compare against *the last value you actually kept*. Both are correct
here. Work out why, and decide which one you can justify in one sentence without
a case analysis about clobbering. Prefer that one. The reason this matters beyond
style: only one of the two generalises cleanly when the rule changes from "keep
one of each" to "keep at most two of each."
