## 1. Pattern

**Family:** Two-pointer in-place compaction — a scan cursor and a write cursor
moving forward at independent rates. Also called read/write or fast/slow
pointers. It is the array-level realisation of a **stable filter**: survivors are
copied forward over territory the scanner has already cleared.

Do not confuse it with the *other* two-pointer family (converging pointers from
both ends). Different shape, different invariant, different problems.

**Trigger:**

> If the problem says **mutate the array in place**, AND the content **beyond a
> returned length `k` is explicitly unconstrained** (or the output is provably no
> longer than the consumed input), AND the keep-decision for an element depends
> only on **elements already kept** (or a fixed-size local window)
> → reach for two pointers, `write` trailing `read`.

Each clause earns its place:

- *In place / O(1) space* is what rules out the collect-and-copy-back solution.
- *Free suffix* is the permission slip. Without it you cannot overwrite, and you
  are back to shifting — O(n²).
- *Decision depends only on what's kept* is what makes the predicate O(1). Drop
  this and you need a hash set, which costs the O(1) space.

A fourth clause is a strong accelerant when present: **sorted input**. Sortedness
is what makes "have I seen this before?" answerable from the last kept element
alone rather than from a set. If a compaction problem gives you sorted input,
that is the sentence doing all the work.

## 2. The transferable trick

> **The output is never longer than the input you have already consumed, so the
> output can live in the input's own prefix.**

That single sentence is the whole idea, and it is stated without reference to
duplicates, sorting, or any specific problem. Everything else is bookkeeping.

The mechanical consequence, which is the thing to actually remember:

> Keep two forward indices. `read` visits every element exactly once. `write`
> advances **only** when an element survives. Because `write` advances no faster
> than `read`, `write <= read` always — and that inequality is the entire safety
> argument. Every store either lands on a cell already consumed, or degenerates
> to `nums[i] = nums[i]`.

Two corollaries worth internalising separately:

- **The write cursor is the answer.** Under the right convention you never
  compute `k`; the cursor *is* `k` at loop exit. Any arithmetic in your return
  statement is a signal your convention is fighting your invariant.
- **The predicate should read the output, not the input.** Compare against what
  you have *kept* (`nums[write-1]`), not against the original neighbour
  (`nums[read-1]`). Both work for the simplest case. Only the first generalises
  the moment the rule becomes "at most two copies," "only values seen an odd
  number of times," or anything else that is a fact about the output. This is the
  single highest-leverage habit in the family.

## 3. The invariant template

Copy this skeleton, fill three placeholders, and the correctness argument comes
along for free.

```java
int compact(int[] a /* , predicate parameters */) {
    // ---- PLACEHOLDER 1: cursor convention. Commit before writing any code.
    // `write` = the NUMBER of elements decided so far, which is simultaneously
    // the INDEX of the next free slot. This convention makes `return write;`
    // need no adjustment. Do not use the "index of last filled slot"
    // convention; it costs you a +1 at every boundary.
    int write = 0;          // or a seed > 0 if the first element(s) are
                            // unconditionally kept — see failure mode 5.2

    // ---- Invariant, true before every iteration:
    //   (1) a[0 .. write-1] == exactly the surviving elements of the ORIGINAL
    //       a[0 .. read-1], in their original relative order; and
    //   (2) write <= read.
    // Clause (2) is the safety property: no unread element is ever destroyed.
    for (int read = 0; read < a.length; read++) {

        // ---- PLACEHOLDER 2: the keep-predicate.
        // Prefer a condition over a[read] and the KEPT prefix a[0..write-1].
        // Guard any a[write - d] access with `write < d ||` to bootstrap.
        if (/* keep(a[read], a[0..write-1]) */ true) {

            // ---- PLACEHOLDER 3: the survive action. Usually a copy-forward.
            // Use a swap instead if the displaced element must be preserved
            // (see adjacent pattern 7.4).
            a[write++] = a[read];
        }
    }

    // read == a.length, so clause (1) now covers the whole array: write == k.
    return write;
}
```

**The discipline that makes this work:** write the invariant comment *first*, then
make the code obey it. Not the reverse. A stated invariant answers your boundary
questions for free — what happens at `n == 0`, at `n == 1`, when the cursors
coincide — which is precisely the class of question that otherwise tempts you into
adding a defensive branch you cannot justify (§ 6.2).

Instantiations, for calibration — every one of these is the skeleton above with
only the placeholders changed:

| Problem | Predicate |
|---|---|
| Dedup sorted array | `write == 0 \|\| a[read] != a[write-1]` |
| Remove all copies of `val` | `a[read] != val` |
| Keep at most 2 of each (sorted) | `write < 2 \|\| a[read] != a[write-2]` |
| Move zeros to the end | `a[read] != 0`, then zero-fill the tail |
| Keep at most `m` of each (sorted) | `write < m \|\| a[read] != a[write-m]` |

## 4. Recognition drill

For each, decide: **does the two-pointer forward-compaction skeleton fire?**
Answer key at the bottom. The near-misses matter more than the hits.

1. Given a sorted array of integers, keep only the values that appear **exactly
   once**, in place, and return the new length.
2. Given an **unsorted** array, remove duplicates keeping the first occurrence of
   each value, in place, in O(1) extra space.
3. Given a sorted array and a target, return the indices of two elements summing
   to the target.
4. Given an array of characters, replace each run of a repeated character with
   the character followed by its run length, writing the result into the same
   array, and return the new length.
5. Given a singly linked list sorted in non-decreasing order, delete all nodes
   with duplicate values so each value appears once.
6. Given an array and a pivot value, rearrange it in place so that all elements
   less than the pivot precede all elements not less than the pivot, and return
   the boundary index. Relative order need not be preserved.
7. Given a string, return the length of the longest substring containing no
   repeated character.
8. Given two sorted arrays where the first has trailing spare capacity, merge the
   second into the first so the result is sorted, in place.

<details>
<summary>Answer key</summary>

1. **FIRES**, with a twist. Same skeleton, but the predicate needs *lookahead* —
   you cannot decide whether `a[read]` survives until you have seen whether the
   next element equals it. The keep-decision becomes a condition on
   `a[read-1]`, `a[read]`, `a[read+1]` (a fixed-size local window, which the
   trigger permits). Worth doing by hand: it is the first variant where "decide
   on sight" breaks.

2. **DOES NOT FIRE.** The predicate is "have I seen this value anywhere before?",
   which is a fact about an unbounded set, not about a fixed window or the tail
   of the kept prefix. You need a `HashSet` — Θ(n) space — and the O(1)-space
   requirement makes the problem as stated **impossible** for arbitrary value
   domains. *Distinguishing question: is the input sorted?* Sortedness is what
   collapses "seen anywhere" into "equals the last one kept." Notice this problem
   is worded almost identically to the source problem; the one deleted word
   changes the complexity class.

3. **DOES NOT FIRE.** This is the *other* two-pointer family: pointers starting
   at opposite ends and **converging**. No write cursor, no compaction, nothing
   is mutated. Shares the phrase "two pointers" and nothing else.
   *Distinguishing question: is anything being written?*

4. **FIRES**, and it is the hardest legitimate member of the family, because the
   safety invariant `write <= read` is **not obvious** — a run of length 1
   expands to 1 output char but a run of length 12 produces 3 (`a12`), so you
   must actually prove the output never overtakes the scanner. It does hold, but
   you owe the argument. This is the variant that punishes anyone who has been
   treating `write <= read` as decoration.

5. **PARTLY.** The predicate is identical ("differs from the last one kept"), but
   the mechanism is pointer relinking, not index arithmetic — there is no
   contiguous storage to compact into, and no `k` to return. The *idea*
   transfers; the *skeleton* does not. Recognising the shared predicate under a
   different data structure is the actual skill here.

6. **FIRES** — this is Lomuto partition, the exact skeleton with predicate
   `a[read] < pivot` and, crucially, **swap instead of copy-forward**. The swap
   is required because the displaced element must survive (it might be needed on
   the other side of the boundary). Note what is *dropped*: relative order is not
   preserved, which is exactly what buys you the O(1) space. Stable partition in
   O(1) space is a much harder problem. See adjacent pattern 7.4.

7. **DOES NOT FIRE.** Sliding window. Both indices move forward, which makes it
   *look* like the same shape, but the trailing index marks the **start of a
   live window** you are still reading from, not a **write destination**. Nothing
   is mutated and no element is discarded. *Distinguishing question: is the
   trailing pointer a destination or a boundary?* This is the most commonly
   confused pair in the whole area.

8. **FIRES**, with the direction reversed. Two read cursors, one write cursor,
   all three running **backwards from the rear**. Reversal is forced: writing
   forward from index 0 would clobber unread elements of the first array, so the
   invariant `write >= read` (mirrored) is what you must maintain instead. Same
   idea, mirrored — and a good test of whether you understand *why* the
   inequality matters rather than just its direction.

**Score 6+ and you have the pattern. If you missed 2 or 7, re-read the trigger in
§ 1 clause by clause — those two are the ones that cost real interviews.**
</details>

## 5. Failure modes for this pattern

These recur across the entire family, independent of the specific predicate.

### 5.1 Index-versus-count confusion at the return
The cursor either counts decided elements (return it bare) or indexes the last
filled slot (return it `+1`). Both work. Mixing them is off-by-one on **every**
input, which — being uniform — is invisible to spot-checking a single example.
**Fix:** commit to the count convention, in a comment, before writing the loop.

### 5.2 Seed and slot disagreement
If you seed `write = 1` (first element unconditionally kept), you must store to
`nums[write]` and compare to `nums[write-1]`. If you seed `write = 0`, the
comparison needs a `write == 0 ||` bootstrap or it reads index `-1`. The two
common crashes:
- `write = 0` plus an unguarded `nums[write-1]` → `ArrayIndexOutOfBounds` on the
  first iteration.
- `write = 0` plus `nums[write] = nums[read]; write++` in a loop starting at
  `read = 1` → silently overwrites index 0 with a later element and returns a
  correct-looking `k` over corrupt data.

### 5.3 Comparing against the input instead of the output
`nums[read-1]` versus `nums[write-1]`. Equivalent for the simplest predicate,
divergent for every extension. See § 2. The tell that you have chosen wrong:
your correctness argument needs a case analysis about whether a cell was
clobbered.

### 5.4 Failing to advance the scan cursor on every path
If `read++` lives inside the keep-branch (common when hand-writing a `while`
instead of a `for`), a rejected element loops forever. **Use a `for` loop** — it
makes the advance structural rather than a thing you must remember.

### 5.5 Comparing forward off the end
`nums[read] != nums[read+1]` reads `nums[n]` on the final iteration. Compare
backward, or bound the loop at `n-1` and handle the tail explicitly.

### 5.6 Assuming `write <= read` instead of proving it
Free for a pure filter (one input element yields at most one output element).
**Not free** when a survivor can expand — run-length encoding, escaping,
interval splitting. In those variants the inequality is a real theorem with a
real proof obligation, and skipping it produces a solution that works on your
examples and corrupts data on a longer run.

### 5.7 Seeded cursors and the empty input
Any solution seeding `write = 1` returns `1` for an empty array. Usually excluded
by a `1 <= n` constraint — but *depending on a constraint deliberately* and
*not noticing you depend on it* look identical in the code and completely
different in an interview. Say it out loud.

### 5.8 Silent failure on precondition violation
Sortedness-dependent predicates return a wrong answer on unsorted input rather
than throwing. Using `>` rather than `!=` binds you to sortedness even harder.
Name the limitation before the interviewer finds it.

### 5.9 Cleaning up after yourself when you were told not to
`Arrays.fill(nums, k, n, 0)` to tidy the tail is Θ(n) wasted writes and signals
you did not read the contract. The suffix is free. (Exception: "move zeros to the
end" genuinely requires the fill, because there the tail *is* specified.)

## 6. Your personal error log for this question

The headline, stated plainly because it is unusual and it is good news:

> **You had no algorithmic weakness on this problem.** Your scan logic in
> attempt 1 was already correct, already Θ(n)/Θ(1), and already the intended
> approach — including the non-obvious safe overwrite. You found the write cursor
> by yourself, by working the problem, in five lines of prose.

What went wrong twice was **justification**, not invention. Both passes show the
same two habits. Treat them as habits, not slips — each appeared in both
attempts, in different clothes.

### 6.1 Habit: you raise the right question, then close it with a guard instead of an answer

This is the important one.

Attempt 1, line 3, unprompted and exactly right:

> *"We compare if c == p, if yes we mark c as replacable r, but now **we'll have
> to track whether the r index is already replaced.**"*

That is the central correctness question of the entire problem: *can I overwrite
a cell I still need to read?* You identified it before I did anything. Then, on
the very next lines, instead of answering it you wrote:

```
int p=0,c=1,u=-1,s=0;
    ...
    if (s!=-1) {          // s starts at 0 and is only ever incremented.
       arr[s+1]=arr[c]    // This condition can never be false.
    }
```

A guard that cannot fire, standing in for a proof that was never constructed.
`u = -1` — the variable that condition was presumably meant to interrogate — was
declared and never used. The worry wasn't discharged; it was upholstered.

Then in attempt 2, given the proof explicitly in `_evaluation1.md § 3.5` and told
in § 8 item 4 that the safety argument was *the section I would grade hardest*,
you shipped:

```java
nums[s+1]=nums[c];   // no comment, no invariant, no proof
```

The proof is four lines (`s = d(c-1) - 1`, so `s+1 <= c`, so the write is either
to a consumed cell or a self-write). It is now in `_answer.md § 3.2`. **You have
still never produced it yourself.**

Same shape on the return value. Attempt 2, line 4, in full:

> *"For missing k value I'd return s+1"*

Correct. And zero reasoning — after § 8 item 2 asked you to commit to a cursor
convention first and let the return *fall out* of it. You applied the hinted fix
without reconstructing why, so you got the right answer on a coin you did not
inspect. Ditto line 5:

> *"The time complexity of code is O(N) and space complexity is O(1)"*

The conclusion with the work deleted — no iteration count, no statement of what
is or isn't allocated, no optimality claim.

**Why this matters more than any bug.** An unjustified correct answer and a
lucky one are indistinguishable from the outside — and, more to the point,
indistinguishable *from the inside*. You cannot tell whether you can transport
the solution to a variant, which is exactly what happened next: you chose the
`nums[c-1]` comparison over `nums[write-1]` after Hint 3 explicitly told you one
of the two doesn't generalise, and then skipped the extension that would have
shown you which. Of the ten deliverables in § 8, **1.5 arrived**. The one labelled
"the real content of pass 2" was among the missing.

**How to break it:** when you notice a worry — and you *do* notice them, that is
the raw talent here — write the sentence that resolves it before you write the
line of code it concerns. If you cannot write the sentence, you have found the
actual hard part of the problem and you should stay there. A guard is never the
answer to "am I sure this is safe?"

### 6.2 Habit: you do not check your own declarations against reachability

Both attempts shipped exactly two branches or variables that cannot affect any
output.

Attempt 1:
```
int p=0,c=1,u=-1,s=0;   // u: declared, never read anywhere
if (s!=-1)              // tautology; s >= 0 always
```
Plus `p`, which was initialised to `c-1` and incremented in the same statement as
`c` forever — so `p == c-1` held at every instant and `arr[p]` was textually
`arr[c-1]`. Not dead, but carrying no information: a variable that looked like a
pointer and was a constant offset.

Attempt 2 deleted all three, and added two more:
```java
if (nums.length == 0) return 0;   // unreachable: the constraints say 1 <= n
if (nums.length == 1) return 1;   // redundant: your own loop already returns 1
```

The second is the same error as `if (s != -1)`, one pass later: a branch added
because you were not certain what your loop does at the boundary, rather than
spending ten seconds finding out. Delete it and trace `[7]` — `while (1 < 1)` is
false immediately, `return s+1` gives `1`. Identical.

(The `length == 0` guard is defensible — it *is* the one case `return s+1`
mishandles — but § 8 item 8 asked for the one sentence saying so, and no sentence
arrived. Unwritten, deliberate judgment is indistinguishable from a hedge.)

Net dead branches: **two in attempt 1, two in attempt 2.** The instances were
fixed; the reflex that generates them was not touched. Note the through-line to
§ 6.1 — a defensive branch *is* a deferred justification. Both habits are the
same underlying move: substituting code for an argument.

**How to break it:** before submitting, take each declaration and each `if` in
turn and name the input that makes it matter. If you cannot name one, delete it.
On a nine-line program this audit costs under a minute and it caught four things
here.

### 6.3 Habit: naming things vaguely, which then hides a decision

Attempt 1 described your cursor as:

> *"an index s which **tracks till what point the array is sorted**"*

That is not what it does. The array is sorted everywhere — that is the
precondition, not a discovery. `s` tracks the extent of the **deduplicated
prefix**. The vague name is what let the count-versus-index question stay open
into attempt 2, where it became the `+1` you guessed rather than derived. Your
prose also introduced an `r` that never appears in the code, and a `u` the prose
never mentions — a reader following along loses the thread.

Rename the cursor `write` and § 6.1's convention question answers itself.

### 6.4 What was slow rather than wrong

- **No brute force, either pass.** You jumped straight to near-optimal, which
  worked out but forfeits the structure that makes an optimal solution look
  *derived*: baseline → price it → name the bottleneck → remove it. It also
  leaves you no fallback.
- **No clarifying questions, either pass.** You *relied* on the suffix beyond `k`
  being free garbage — it is what licenses the entire approach — without ever
  asking or stating it.
- **Both passes were prose-only where code was asked for, or code-only where
  prose was asked for.** Pass 1 was strong reasoning attached to broken code;
  pass 2 was correct code attached to almost no reasoning. You have now
  demonstrated each half separately. The bar is both at once, and you are
  evidently capable of both.

### 6.5 The one-line summary to carry forward

> Your instincts find the right algorithm and the right doubts. What you skip is
> writing down why — and you substitute a guard for the argument. The pattern
> costs nothing on a problem you happen to get right, and everything on the first

## 7. Adjacent patterns

### 7.1 Converging two pointers (opposite ends, moving inward)
Two-sum on sorted input, palindrome check, container-with-most-water, reversing
in place, trapping rain water.
**Distinguishing question: are the pointers moving toward each other, and is
anything being written?** Compaction has both cursors moving forward and one of
them is a write destination. Converging pointers usually mutate nothing (or swap
symmetrically) and return an answer rather than a length.

### 7.2 Sliding window (both forward, trailing pointer is a boundary)
Longest substring without repeats, minimum window substring, max sum subarray of
size k.
**Distinguishing question: is the trailing pointer a write destination or the
start of a live region you are still reading from?** This is the most-confused
pair in the area, because both have two forward-moving indices at different
rates. In compaction the trailing index points at a *hole you fill*; in a sliding
window it points at *data you still need*. Also: compaction discards elements
permanently; a window only stops considering them.

### 7.3 Read-ahead / lookahead compaction
"Keep only elements appearing exactly once," "remove all runs of length > 1."
Still the compaction skeleton, but the predicate needs `a[read+1]` because you
cannot decide on sight.
**Distinguishing question: can I decide this element's fate from what I've
already seen?** If no, you need lookahead, a run-detecting inner loop, or a
deferred write — and your loop bound needs care (failure mode 5.5).

### 7.4 In-place partition (swap instead of copy-forward)
Lomuto/Hoare partition, sort-colours, segregate even and odd.
**Distinguishing question: must the element being displaced survive?** If yes,
swap; if it is garbage you are allowed to destroy, copy forward. The tell is
whether the problem specifies content on *both* sides of the boundary — a filter
specifies only the prefix, a partition specifies the whole array. Note also that
partition typically **sacrifices relative order**, and that sacrifice is what
buys the O(1) space; stable in-place partition is a genuinely harder problem.

### 7.5 Hash-set dedup
The unsorted version of this problem.
**Distinguishing question: is the input sorted?** If not, "seen before" is a fact
about an unbounded set and the O(1)-space requirement becomes unsatisfiable for
arbitrary value domains. Deleting the word "sorted" from a compaction problem
changes its complexity class — recognise that instantly (drill § 4 item 2).

### 7.6 Rear-anchored merge
Merging a sorted array into another with trailing capacity.
**Distinguishing question: would writing forward clobber data I still need?** If
yes, reverse the direction and maintain the mirrored inequality. Same idea,
mirrored — and a good check on whether you understand *why* `write <= read`
matters rather than just its direction.
