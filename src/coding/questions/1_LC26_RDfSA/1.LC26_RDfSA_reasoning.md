# 1. LC26 — Remove Duplicates from Sorted Array — Pass 0 Reasoning

> Independent solve, written before any user attempt. Do not read this until
> `_pass1.md` and `_pass2.md` are both written.

---

## 1. Restatement

Given an array of integers already sorted in non-decreasing order, collapse each
run of equal values down to a single occurrence, keeping the surviving elements
in their original (sorted) order, and do it without allocating a second array.
Return `k`, the count of distinct values; the caller only inspects `nums[0..k-1]`.

**The contract, precisely:**

| Obligation | What it actually means |
|---|---|
| Input | `int[] nums`, sorted non-decreasing, length ≥ 1. |
| Return | `int k` = number of distinct values in `nums`. |
| Mutation | After return, `nums[i]` must equal the `i`-th smallest *distinct* value, for every `0 ≤ i < k`. |
| Beyond `k` | Unconstrained. Anything may sit at `nums[k..n-1]` — old values, duplicates, garbage. **No obligation to clear, zero, or truncate.** |
| "In-place" | O(1) auxiliary space. Writing into `nums` is permitted and required; allocating a second `int[n]` and copying back is *not* in-place even though the signature would still work. |

The judge is what defines correctness here, and it reads only the prefix. That
asymmetry — a strict prefix and a free suffix — is the whole exploitable
structure of the problem.

---

## 2. Constraint reading

| Constraint | What it rules in / out | Signal |
|---|---|---|
| `nums is sorted in non-decreasing order` | Duplicates are necessarily **adjacent**. Detecting a duplicate never requires memory of anything but the immediately preceding kept element. This is *the* constraint; without it the problem is a different (hash-set / O(n log n)) problem. | Strong signal for a **single linear scan with local comparison**. |
| `1 <= nums.length <= 3 * 10^4` | n is small. O(n²) = 9·10⁸ — borderline-to-too-slow in Java, so quadratic (e.g. repeated `System.arraycopy` shifting on every duplicate) is *not* safe. O(n log n) would pass comfortably. O(n) is trivially fine. | Rules out the naive "shift-left on delete" approach as the intended answer; rules in anything linear or linearithmic. |
| `1 <=` (lower bound on length) | The array is **never empty**. No `n == 0 → return 0` guard is strictly required. I will still write the code so it degrades gracefully, but I should *notice* that the constraint gives it to me for free — an interviewer may ask "what if it were 0?" | Removes one edge case; invites the interviewer's follow-up. |
| `-100 <= nums[i] <= 100` | Only 201 possible values ⇒ `k ≤ 201` regardless of n. A counting-array approach (201 buckets) is *possible* in O(n + 201) time and O(1)-by-constant space. | This is a **decoy**. It hints at counting sort, but counting throws away the sortedness we were handed and is strictly worse than the linear scan. Worth naming in an interview as "considered and rejected, here's why." |
| Negative values allowed | A sentinel like `Integer.MIN_VALUE` for "no previous element" is safe, but `-1` or `0` as a sentinel is **not**. | Kills the lazy `int prev = 0;` initialisation. |
| Return `k`, judge ignores suffix | No need to shrink, null out, or `Arrays.fill` the tail. | Permits **overwriting forward** rather than deleting. |

The two constraints that do real work: *sorted* (duplicates are adjacent) and
*suffix is free* (I can write over positions I have already read past).

## 3. Clarifying questions I would ask an interviewer

1. **"Can I destroy the contents beyond index `k-1`, or must the tail be zeroed / preserved?"**
   *Assumption if unanswered:* the tail is free garbage. The problem statement's
   underscores confirm it, but asking shows I read the contract rather than the examples.

2. **"Must the returned array region be a genuine in-place mutation of the input, or may I allocate an O(n) buffer and copy back?"**
   *Assumption:* strict O(1) auxiliary space. Assume the harder contract; it costs nothing here.

3. **"Is 'non-decreasing' guaranteed by the caller, or should I validate it?"**
   *Assumption:* guaranteed, no validation. If it were *not* guaranteed, my algorithm silently returns a wrong answer rather than throwing — worth stating aloud.

4. **"Is the array huge enough that I should care about cache behaviour or memory bandwidth, or is n ≤ 3·10⁴ the real bound?"**
   *Assumption:* n ≤ 3·10⁴, so a single sequential pass is unquestionably fine and I optimise for clarity.

5. **"Do you want me to minimise writes as well as reads — e.g. is this backed by flash / a write-amplified medium?"**
   *Assumption:* writes are as cheap as reads. But this question sets up the
   "skip the self-write when `write == read`" refinement, which is a genuine
   improvement and a nice thing to have anticipated.

6. **"Should duplicates be defined by `==` on the int, or could this generalise to objects with a custom comparator/equality?"**
   *Assumption:* primitive `int` equality. The generalisation matters if the
   follow-up is "now do it for `T[]` with a `Comparator<T>`", where "equal" means
   `cmp.compare(a,b) == 0` and the *first* of each equal run must be retained for stability.

## 4. Brute force

**Idea.** Forget in-place. Walk the array; push a value onto a growable list only
if it differs from the last pushed value; then copy the list back over the front
of `nums` and return its size.

```java
int removeDuplicatesBrute(int[] nums) {
    List<Integer> unique = new ArrayList<>();
    for (int value : nums) {
        if (unique.isEmpty() || unique.get(unique.size() - 1) != value) {
            unique.add(value);
        }
    }
    for (int i = 0; i < unique.size(); i++) {
        nums[i] = unique.get(i);
    }
    return unique.size();
}
```

**Complexity.** Time O(n): one pass to build, one pass to copy back, each
amortised O(1) per element. Space **O(k)** auxiliary — up to O(n) when the input
is all-distinct.

**Why it is unacceptable here.** It passes the judge but violates the stated
in-place requirement, which is the entire point of the exercise. It also boxes
every element (`Integer` autoboxing) — 3·10⁴ allocations plus `intValue()`
unboxing on each comparison, and the `!=` on line 4 is comparing *unboxed* ints
only because the right operand is an `int`; had both sides been `Integer` it
would have compared references and broken silently outside the cache range
`[-128, 127]`. That is a real, subtle Java trap worth naming.

There is a *worse* brute force worth mentioning and dismissing: for each
duplicate found, `System.arraycopy` the remainder of the array one slot left.
That is O(n²) in the worst case (all elements equal ⇒ n−1 shifts of ~n elements
= 4.5·10⁸ element moves at n = 3·10⁴). It is genuinely in-place but too slow,
and it is the most common instinct — "remove" sounds like "delete and shift."

## 5. The chain of improvements

**Observation 1 — the list is redundant.**
*Observation:* I build `unique` left-to-right and it is always a **prefix-sized**
structure: after processing `nums[0..i]`, `unique` holds at most `i+1` elements.
*Consequence:* `unique.size() ≤ i + 1` at all times, so the region
`nums[0..unique.size()-1]` never extends past the region I have already read.
*New approach:* store `unique` **inside `nums` itself**, at the front. The
"append" becomes a write to `nums[writeIndex++]`. No auxiliary structure, no
copy-back phase. This is the key move: the output is strictly no longer than the
consumed input, so output and input can share storage.

**Observation 2 — I do not need the list to know the last kept value.**
*Observation:* `unique.get(unique.size()-1)` is just "the most recently kept element."
*Consequence:* once the list lives in `nums`, that is `nums[writeIndex - 1]`.
*New approach:* comparison becomes `nums[read] != nums[write - 1]`. Two integer
indices are the entire state. This is the **slow/fast (read/write) two-pointer
compaction** pattern.

**Observation 3 — sortedness lets me compare to the neighbour instead.**
*Observation:* the last *kept* value and the *immediately preceding* value in the
original array are always equal, because duplicates form contiguous runs and I
keep the first of each run.
*Consequence:* `nums[read] != nums[write - 1]` and `nums[read] != nums[read - 1]`
are interchangeable **only if `nums[read-1]` has not yet been overwritten**.
Since `write ≤ read` always, `nums[read-1]` *can* have been clobbered when
`write == read`… but in that case `write - 1 == read - 1`, so they are literally
the same cell. And when `write < read`, cell `read-1` is untouched. So both
formulations are correct. I prefer comparing against `nums[write - 1]` because
its correctness argument is local ("compare to what I last kept") and does not
depend on that clobbering case analysis.

**Dead end A — `Set<Integer>` / `LinkedHashSet`.**
Works for any input, sorted or not, O(n) time, but O(k) space and it *ignores the
sortedness*. Abandoned: it solves a strictly harder problem at strictly worse cost.
Mentioning it in an interview is good; proposing it as the answer is not.

**Dead end B — counting array over `[-100, 100]`.**
`boolean[] seen = new boolean[201]`, index by `nums[i] + 100`, then write out the
seen values in ascending index order. O(n + 201) time, O(201) auxiliary — "O(1)"
only by the courtesy of a fixed alphabet. Abandoned for three reasons: it
allocates, it is not in-place in spirit, and it would break the instant the
value-range constraint is relaxed (which is exactly the follow-up an interviewer
asks). The value range is bait.

**Dead end C — `Arrays.stream(nums).distinct()`.**
```java
int[] u = Arrays.stream(nums).distinct().toArray(); // O(n) space, allocates
```
One line, correct output if copied back, but it allocates and internally uses a
hash-based distinct that does not exploit sortedness. Fine as a "here's the
one-liner if this were production and n were small" aside; not the answer.

**Dead end D — shift-on-delete (`System.arraycopy` per duplicate).**
Genuinely O(1) space and genuinely in-place, but O(n²) time. Rejected on the
constraint analysis in § 2. It is the trap the word "remove" sets.

**Observation 4 — the first element is always kept.**
*Observation:* with n ≥ 1, `nums[0]` is by definition the first element of the
first run.
*Consequence:* I can seed `write = 1` and start reading at `read = 1`, which
removes the `if (write == 0)` special case from the loop body entirely. The loop
becomes a single unconditional comparison. Fewer branches, and the invariant is
easier to state because `write ≥ 1` holds throughout.

**Observation 5 (micro) — the self-write.**
*Observation:* when no duplicates exist yet, `write == read` and
`nums[write] = nums[read]` writes a cell to itself.
*Consequence:* on an all-distinct input we perform n−1 pointless stores.
*New approach:* guard with `if (write != read)`. This trades a predictable branch
for a store. On modern hardware it is a wash and it clutters the code, so I
**would not** ship it — but I would name it, because it is exactly the answer to
clarifying question 5 (write-expensive media).

## 6. Optimal approach

**Technique.** Two-pointer in-place compaction (read/write, a.k.a. fast/slow).

**Invariant.** Immediately before each iteration of the loop, with `read` the
next index to examine and `write` the next index to fill:

> `nums[0 .. write-1]` contains exactly the distinct values of the original
> `nums[0 .. read-1]`, in ascending order, and `1 ≤ write ≤ read ≤ n`.

Three corollaries fall out of it:
- `write ≤ read` guarantees the write pointer never runs ahead of the read
  pointer, so **no unread datum is ever destroyed**. This is the safety property.
- `write ≥ 1` guarantees `nums[write - 1]` is always a valid, already-decided
  element — the last value we kept.
- At loop exit `read == n`, so the invariant reads: `nums[0..write-1]` holds
  exactly the distinct values of the whole array. Therefore `write` is `k`.

**Code (Java 21).**

```java
class Solution {

    /**
     * Collapses runs of equal values in a non-decreasing array, in place.
     *
     * @param nums sorted non-decreasing, length >= 1
     * @return k, the number of distinct values now occupying nums[0..k-1]
     */
    public int removeDuplicates(int[] nums) {
        // nums[0] is always the first element of the first run, so it is kept
        // unconditionally and write starts at 1.
        int write = 1;

        // Invariant (holds before every iteration):
        //   nums[0 .. write-1] == distinct values of original nums[0 .. read-1],
        //   in ascending order, and 1 <= write <= read <= nums.length.
        for (int read = 1; read < nums.length; read++) {
            if (nums[read] != nums[write - 1]) {
                nums[write++] = nums[read];
            }
        }

        return write;
    }
}
```

Twelve lines counting the comment. `write` is the answer; there is no separate
counter to keep in sync, which removes an entire class of bug.

**Why `nums[write - 1]` and not `nums[read - 1]`.** Both are correct (§ 5,
observation 3), but the `write - 1` form reads as "is this different from the
last thing I decided to keep?", which is a direct restatement of the invariant.
The `read - 1` form requires the reader to prove that `nums[read - 1]` has not
been clobbered. Prefer the version whose correctness argument is one sentence.

### Dry run — Example 1: `nums = [1,1,2]`, n = 3

Initial: `write = 1`, array `[1,1,2]`.

| read | nums[read] | write | nums[write-1] | differ? | action | array after | write after |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 1 | nums[0]=1 | no | skip | `[1,1,2]` | 1 |
| 2 | 2 | 1 | nums[0]=1 | yes | `nums[1]=2` | `[1,2,2]` | 2 |

Loop exits (`read = 3 = n`). Return `write = 2`. Prefix `nums[0..1] = [1,2]`. ✓
Matches expected `2, [1,2,_]` — the trailing `2` at index 2 is the free suffix.

### Dry run — Example 2: `nums = [0,0,1,1,1,2,2,3,3,4]`, n = 10

Initial: `write = 1`, array `[0,0,1,1,1,2,2,3,3,4]`.

| read | nums[read] | write | nums[write-1] | differ? | action | array after | write after |
|---|---|---|---|---|---|---|---|
| 1 | 0 | 1 | nums[0]=0 | no | skip | `[0,0,1,1,1,2,2,3,3,4]` | 1 |
| 2 | 1 | 1 | nums[0]=0 | yes | `nums[1]=1` | `[0,1,1,1,1,2,2,3,3,4]` | 2 |
| 3 | 1 | 2 | nums[1]=1 | no | skip | `[0,1,1,1,1,2,2,3,3,4]` | 2 |
| 4 | 1 | 2 | nums[1]=1 | no | skip | `[0,1,1,1,1,2,2,3,3,4]` | 2 |
| 5 | 2 | 2 | nums[1]=1 | yes | `nums[2]=2` | `[0,1,2,1,1,2,2,3,3,4]` | 3 |
| 6 | 2 | 3 | nums[2]=2 | no | skip | `[0,1,2,1,1,2,2,3,3,4]` | 3 |
| 7 | 3 | 3 | nums[2]=2 | yes | `nums[3]=3` | `[0,1,2,3,1,2,2,3,3,4]` | 4 |
| 8 | 3 | 4 | nums[3]=3 | no | skip | `[0,1,2,3,1,2,2,3,3,4]` | 4 |
| 9 | 4 | 4 | nums[3]=3 | yes | `nums[4]=4` | `[0,1,2,3,4,2,2,3,3,4]` | 5 |

Loop exits (`read = 10 = n`). Return `write = 5`. Prefix `nums[0..4] = [0,1,2,3,4]`. ✓
Matches expected `5, [0,1,2,3,4,_,_,_,_,_]`. Note row 5 and row 7: the write
lands on a cell (`index 2`, `index 3`) whose old value had *already been read* —
the `write ≤ read` invariant is what makes that safe, and the messy-looking
suffix `[...,2,2,3,3,4]` is precisely the debris the contract permits.

## 7. Complexity

**Time — Θ(n).**
The loop body executes exactly `n − 1` times (`read` runs `1 … n−1`, incremented
once per iteration, never reset). Each body is one array read, one comparison,
and at most one array write plus one increment — all O(1). Total
`(n−1) · O(1) + O(1)` setup `= Θ(n)`. Not just O(n): it is also Ω(n), and it must
be, since any correct algorithm has to inspect every element (skipping one could
miss a distinct value). So this is **optimal in time**, not merely linear.

Write count specifically: exactly `k − 1` stores in the best case if we add the
`write != read` guard; up to `n − 1` stores without it. Reads: exactly
`2(n−1)` array accesses (`nums[read]` and `nums[write-1]`), which is why one
might cache the last kept value in a local `int last` — a register instead of a
memory load. Immaterial at n = 3·10⁴.

**Space — Θ(1).**
Two `int` locals, `read` and `write`. No allocation of any kind: no array, no
collection, no boxing, no recursion (so no stack growth). The input array is
mutated in place, which the contract requires. Total auxiliary = 8 bytes,
independent of n.

## 8. Edge cases

| Case | Input | Why it is dangerous | What the code does |
|---|---|---|---|
| Single element | `[7]` | Loop must not execute; naive code that reads `nums[1]` or seeds `write = 0` and compares `nums[-1]` throws. | `write = 1`; `for (read = 1; 1 < 1; ...)` never runs; returns 1. Prefix `[7]`. ✓ |
| All identical | `[3,3,3,3]` | Worst case for shift-on-delete (O(n²)); also the case where `write` stops advancing entirely. | No comparison ever succeeds; `write` stays 1; returns 1. Array left `[3,3,3,3]`, prefix `[3]`. ✓ |
| All distinct | `[1,2,3,4]` | Every iteration writes; `write == read` throughout, so every store is a self-write. Correctness risk if someone "optimises" by writing to `nums[write]` *before* incrementing incorrectly. | Each store is `nums[i] = nums[i]`, harmless. Returns 4. ✓ |
| Two elements, equal | `[5,5]` | Smallest input that must actually collapse. | read=1: `nums[1]==nums[0]`, skip. Returns 1. ✓ |
| Two elements, distinct | `[5,6]` | Smallest input that must not collapse. | read=1: differ, `nums[1]=6`, write=2. Returns 2. ✓ |
| All negative | `[-100,-100,-1]` | Kills any implementation using `0` or `-1` as a "no previous value" sentinel. | No sentinel used — the seed is `nums[0]` itself, via `write = 1`. Returns 2, prefix `[-100,-1]`. ✓ |
| Contains the boundary values | `[-100, 100]` | Tempts an `int prev = Integer.MIN_VALUE` sentinel, which is fine, versus `prev = -101` reasoning that breaks if the range widens. | Unaffected — no sentinel. ✓ |
| Duplicate run at the very end | `[1,2,3,3]` | Off-by-one risk: the final run must not push `write` past `k`. | read=3: `nums[3]==nums[write-1]=nums[2]=3`, skip. Returns 3. ✓ |
| Duplicate run at the very start | `[9,9,9,10]` | `write` must not advance during the leading run; a `write = 0` seed plus an unguarded `nums[write-1]` would read index −1. | `write = 1` seed avoids the negative index entirely. Returns 2. ✓ |
| Long run in the middle | `[1,2,2,2,2,3]` | The gap `read − write` grows; must not corrupt unread data. | `write ≤ read` invariant holds; write at index 2 happens only at read = 5, after index 2 was consumed at read = 2. Returns 3. ✓ |
| Empty array | `[]` | **Excluded by the constraint `1 <= nums.length`**, but the classic interview follow-up. | `write = 1` would be returned — **wrong**, it should be 0. If the constraint were relaxed I would need `if (nums.length == 0) return 0;`. Worth saying aloud: "my seed of `write = 1` bakes in the length ≥ 1 guarantee; here's the one-line guard if you drop it." |
| `null` input | `null` | Not in the contract. | NPE on `nums.length`. Acceptable — fail fast — but I would state the choice rather than let it look accidental. |
| Unsorted input | `[3,1,3]` | Precondition violation. | Returns 3 with prefix `[3,1,3]` — silently wrong, no exception. This is the honest limitation to name: the algorithm's correctness rests entirely on the sortedness precondition, and it fails *quietly*, not loudly. |

The `[]` row is the one I would volunteer unprompted. Reading `1 <=` in the
constraints and then explicitly choosing to depend on it — rather than not
noticing it — is the difference between a lucky solution and a deliberate one.

## 9. How I would present this in an interview

Roughly 60 seconds before writing a line of code, then code, then verify.

> **Clarify (10s).** "The array is sorted, so duplicates are adjacent — that's
> the lever. Two things I want to confirm: I can leave arbitrary garbage beyond
> index k−1, right? And by in-place you mean O(1) extra space, so no second
> array even if I copy it back?"
>
> **Brute force (10s).** "The obvious version collects distinct values into a
> list and copies them back — O(n) time but O(k) extra space, so it fails the
> in-place requirement. And the instinct that 'remove' means shift-left on every
> duplicate is O(n²): all-equal input gives ~n shifts of ~n elements, about
> 9·10⁸ moves at the upper bound, too slow."
>
> **Bottleneck (10s).** "The list is the only thing costing me space, and it's
> redundant: after processing the first `i` elements it holds at most `i`
> entries. The output is never longer than the input I've already consumed — so
> the output can live in the input array's own prefix."
>
> **Optimal (20s).** "Two pointers. `write` marks where the next kept element
> goes, `read` scans. Seed `write = 1` because `nums[0]` is always kept, and
> that also kills the `write-1 == -1` edge case. For each `read`, compare
> `nums[read]` to `nums[write-1]` — the last value I kept; if it differs, it
> starts a new run, so store it at `nums[write]` and advance. The invariant is
> that `nums[0..write-1]` is exactly the distinct values of the original
> `nums[0..read-1]`, and `write ≤ read` always, which is what guarantees I never
> overwrite something I haven't read yet. At exit `read == n`, so `write` is `k`."
>
> **Complexity (5s).** "Θ(n) time — n−1 iterations of constant work, and Ω(n) is
> a lower bound since every element must be inspected, so this is optimal. Θ(1)
> space: two ints."
>
> **Test (10s).** "Let me run `[0,0,1,1,1,2,2,3,3,4]`… returns 5, prefix
> `[0,1,2,3,4]`. Single element `[7]`: loop doesn't run, returns 1. All-equal
> `[3,3,3]`: `write` never advances, returns 1. And note the constraint says
> length ≥ 1 — I'm relying on that for the `write = 1` seed; if you want to
> allow an empty array I'd add a one-line guard returning 0."

Then, if there is time, volunteer the follow-up axis unprompted: *"the natural
extension is 'allow each element at most twice' — same skeleton, you just compare
against `nums[write - 2]` instead of `nums[write - 1]` and seed `write = 2`."*
That single sentence demonstrates you understand the pattern rather than the
puzzle, and it is LeetCode 80.

## 10. Pattern name

**Family:** Two-pointer in-place array compaction (read/write pointers, also
called fast/slow or scan/fill). A subfamily of the *stable partition / filter*
pattern: `write` is a compaction cursor for elements passing a keep-predicate,
and `write ≤ read` is the universal safety invariant of the family.

**Trigger, one line:**

> If the problem says **modify the array in place**, allows **arbitrary content
> beyond a returned length `k`**, and the keep-decision for an element depends
> only on **elements already kept** (or on a local window) → reach for two
> pointers, `write` trailing `read`.

The sortedness is what makes the keep-predicate *local* here ("differs from the
last kept"). Drop sortedness and the skeleton survives but the predicate needs a
hash set, which costs the O(1) space. The skeleton is the transferable part:

```java
int write = 0;
for (int read = 0; read < n; read++) {
    if (keep(nums[read])) {   // predicate over nums[read] and nums[0..write-1]
        nums[write++] = nums[read];
    }
}
return write;
```

Same skeleton, different predicate, drives LC 27 (remove element), LC 80 (allow
duplicates twice), LC 283 (move zeroes), LC 443 (string compression), and
`List.removeIf`'s own implementation in the JDK.
