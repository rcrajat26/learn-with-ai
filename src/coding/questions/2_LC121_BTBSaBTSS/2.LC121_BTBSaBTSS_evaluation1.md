## 2. What you got right

Concrete credit, not encouragement:

- **You floored the result at 0.** `abs_max - abs_min > 0 ? abs_max - abs_min : 0`
  is exactly right, and it is the detail that makes `n == 1` and the
  all-decreasing case fall out for free. A lot of attempts seed a "best" at
  `Integer.MIN_VALUE` and then return a negative number on `[7,6,4,3,1]`.
- **Your sentinels are correctly chosen.** `abs_min = Integer.MAX_VALUE` and
  `abs_max = Integer.MIN_VALUE` are right, and specifically *not* `0` — which
  matters here because `0` is a legal price (`0 <= prices[i]`). You avoided a
  real trap without commenting on it; make that reasoning explicit next time.
- **You self-diagnosed the infinite loop correctly.** Advancing `i` only inside
  the `if` means a non-improving element never moves the pointer, so the loop
  spins forever on the first non-minimum. Hoisting `i++; j--;` out of the
  conditionals is the correct fix to *that* bug, and you found it unaided.
- **You constructed a failing input yourself** rather than waiting for the
  judge to tell you which one. `[3,2,6,5,0,3]` is a genuinely good adversarial
  case. Building counterexamples is the skill that matters most here.
- **You stopped and asked instead of thrashing.** Correct call. Attempt 2 will
  be worth more than another hour on a dead approach.

## 3. What breaks

### Defect 1 — the fatal one: the algorithm is order-blind

Your quantity is "biggest value seen minus smallest value seen". The problem's
quantity is "biggest value seen **after** the smallest value used". Those are
different, and the difference is the entire problem.

**Killer input:** `prices = [2, 1]`. Expected output `0` — the high day is day 0,
the low day is day 1, so there is no legal buy-then-sell pair with positive
profit.

Your trace: `i=0, j=1`. `prices[0]=2 < MAX_VALUE` → `abs_min = 2`.
`prices[1]=1 > MIN_VALUE` → `abs_max = 1`. Then `i=1, j=0`, `i>j`, break.
`abs_max - abs_min = 1 - 2 = -1`, floored → returns `0`. **Correct — by
accident.** The pointers happened not to see the pair in the order that would
have produced the wrong answer.

Now the same shape with more room: `prices = [9, 1, 2]`. Expected `1` (buy day 1
at 1, sell day 2 at 2). Your trace: `i=0, j=2` → `abs_min=9`, `abs_max=2`;
`i=1, j=1` → `prices[1]=1 < 9` so `abs_min=1`; `prices[1]=1 > 2`? no. Then
`i=2, j=0`, break. Returns `2 - 1 = 1`. Also correct by accident.

The order-blindness bites hardest once both extremes are *seen*. Which brings us
to the input you found.

### Defect 2 — pointer coverage: elements never examined

**Your input:** `prices = [3,2,6,5,0,3]`. Expected output **4** (buy day 1 at 2,
sell day 2 at 6).

Your trace, which matches yours exactly:

| step | `i` | `j` | `prices[i]` | `prices[j]` | `abs_min` | `abs_max` |
|---|---|---|---|---|---|---|
| init | 0 | 5 | 3 | 3 | MAX | MIN |
| 1 | 0 | 5 | 3 | 3 | 3 | 3 |
| 2 | 1 | 4 | 2 | 0 | 2 | 3 |
| 3 | 2 | 3 | 6 | 5 | 2 | 5 |
| — | 3 | 2 | — | — | break | break |

Returns `5 - 2 = 3`. Expected `4`. The `6` at index 2 was only ever read by `i`,
which is the pointer that looks for minima, so it never reached `abs_max`.

**But here is the part your notes get wrong.** Your conclusion was:

> "The J never got to reach 2nd index. We must allow i and j both look through
> all the values."

Test that fix before you build on it. Suppose both pointers *do* sweep the whole
array, so `abs_min = min(all) = 0` and `abs_max = max(all) = 6`. Your return is
then `6 - 0 = 6`. Expected is still `4`. **The full-coverage version is more
wrong, not less.** The `0` sits at index 4 and the `6` sits at index 2 — you
cannot buy on day 4 and sell on day 2.

So defect 2 is real, but repairing it does not get you to a correct algorithm.
It just converts a wrong answer into a differently wrong answer. Do not spend
attempt 2 fixing the pointer bounds.

### Defect 3 — the reasoning gap underneath both

The step that does not follow is the very first line of your attempt:

> "I will try running two pointers one from left and another from right"

Two-pointer-from-both-ends is the right reflex for problems where the *pair* is
symmetric — container-with-most-water, two-sum-on-sorted, palindrome checks.
There, moving either pointer inward is a provably safe discard. Here the pair is
**asymmetric**: one element must be the buy and it must come first. A right-hand
pointer walking leftward is walking backwards through causality. There is no
discard argument that justifies shrinking the window from the right, and you
never tried to write one — that is the missing step. Whenever you reach for
converging pointers, force yourself to say out loud *"moving `j` left is safe
because ..."*. If you cannot finish that sentence, the pattern does not apply.

### Defect 4 — a latent crash your edge-case list papers over

You wrote:

> "Array size is 0, return 0"

Your code does not do this. With `n == 0`, `i = 0` and `j = -1`, the guard
`while (i < n || j >= 0)` is `(0 < 0) || (-1 >= 0)` = `false`, so the loop is
skipped and you return `MIN_VALUE - MAX_VALUE` floored — which in `int`
arithmetic is `-2147483648 - 2147483647`, wrapping to `1`. You would return `1`
for an empty array, not `0`. Harmless here (the constraint guarantees
`length >= 1`), but the listed edge case is not the behaviour of the code. When
you write an edge-case list, trace it; do not assert it.

Also note `while (i < n || j >= 0)` uses `||` where the loop's real termination
is the `break`. The condition is doing nothing, and with `||` rather than `&&` it
would happily let `i` run past `n-1` and read out of bounds if the `break` were
ever removed or reordered. A loop whose guard is decorative is a loop whose guard
is a future bug.

## 7. Hints

Graduated. Read one, close the file, and try. Only come back if you are still
stuck.

### Hint 1 — nudge

Ask yourself one question, and answer it honestly in writing before touching
code:

> **Does my algorithm's output depend on the *order* of the array, or only on
> the *set* of values in it?**

Concretely: what does your method return for `[2, 1]` versus `[1, 2]`? Both
contain the same two numbers. The correct answers are `0` and `1`. If your
method cannot distinguish two arrays that differ only by a permutation, it can
never be correct — because the entire content of this problem is the sentence
*"a different day **in the future**"*.

Second nudge, on process rather than on the algorithm: write the brute force
first. All of it, `O(n²)`, nested loops, no cleverness. You need a definition of
the answer you can trust before you can recognise an optimisation as valid.
Then look hard at the two loops and ask which of them is doing redundant work.

### Hint 2 — stronger

You have been trying to find **both** endpoints of the answer at the same time.
That is what the converging two-pointer setup is: a simultaneous search for the
buy and the sell. Abandon it. It is the source of every problem above.

Instead, **fix one endpoint and ask what the best partner is.**

Pick the *sell* day. Say you have committed to selling on day `j` — that
decision is now frozen. Answer these three questions:

1. Which days are legal buy days, given that you sell on day `j`?
2. Among those legal buy days, which single one do you want, and why is the
   choice obvious once the sell day is fixed?
3. Therefore: what is the best possible profit for a sale on day `j`, expressed
   as `prices[j]` minus *one number*?

Now: the real answer is the best over all choices of `j`. So sweep `j` across the
array and take the maximum of that per-day quantity. That is already a correct
algorithm. Write it — even if your first version needs a helper array or a
second pass. **A correct `O(n)`-with-extra-space solution is worth far more than
another wrong one-liner**, and it is the honest stepping stone to the final form.

The last thing to notice, once that version works: as `j` moves left to right,
how expensive is it to keep "the one number" from question 3 up to date? Does it
need recomputing from scratch each time, or can it be *maintained*?

### Hint 3 — near-giveaway

Technique name: **single forward pass with a running prefix extremum** — one
loop, left to right, `O(n)` time and `O(1)` extra space. Equivalently framed:
one-dimensional dynamic programming whose state collapses to a single scalar.
(There is a second, equivalent framing via the array of day-to-day differences
that turns this into a classic named problem; you do not need it to solve this,
and I will show it in the answer pass.)

You carry exactly **two** `int` variables across iterations, and nothing else.
One of them is the answer-so-far, seeded at `0` — you already had that instinct
in attempt 1, keep it. The other is an aggregate over the part of the array
you have already walked past.

The invariant has this shape. Fill in the blanks yourself; do not look them up:

```
Entering the iteration for index i:
    <var A> == ____ of prices[0 .. i-1]      // note the range: it EXCLUDES i
    <var B> == the answer for the sub-array prices[0 .. i-1], floored at 0
```

Two things decide whether your code is correct, and they are both about the
loop body rather than the loop bounds:

- The range in that first line ends at `i-1`, not `i`. Ask what goes wrong if it
  ended at `i`, and which rule of the problem statement that would violate.
- The body performs two updates. **Their order is the whole correctness
  argument.** One of them must happen strictly before the other. Work out which,
  by reference to the range above — then write that reason as a comment on the
  line. If you cannot state the reason, you have a coin flip, not a proof.

Still no code and no full algorithm from me. Everything above is a description
of the shape; you write the mechanism.
