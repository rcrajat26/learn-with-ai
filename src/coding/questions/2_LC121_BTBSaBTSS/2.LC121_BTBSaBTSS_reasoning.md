# 2. LC121 — Best Time to Buy and Sell Stock — my independent reasoning

Written before seeing any user attempt. This is a worked derivation, not a
solution dump; read it only after pass 2.

---

## 1. Restatement

Given an array `prices` indexed by day, pick one buy day `i` and one sell day
`j` with `j > i`, and maximise `prices[j] - prices[i]`. Exactly one buy and one
sell — no re-entry, no shorting, no holding two lots. If every such pair yields
a non-positive value, the answer is `0` (the "do nothing" transaction is always
available).

**Contract.**

| Item | Obligation |
|---|---|
| Input | `int[] prices`, length ≥ 1, values in `[0, 10^4]` |
| Output | `int` — the maximum of `prices[j] - prices[i]` over all `j > i`, floored at 0 |
| Mutation | None required; do not mutate the input |
| `j > i` | Strict. Buying and selling on the same day is not a transaction, and it would yield 0 anyway — so the floor-at-0 rule silently subsumes it |
| Return 0 | Not a sentinel for "impossible". It is a real answer: decline to trade |

The floor-at-0 detail is the one that quietly rescues a lot of implementations:
because 0 is always achievable, we never have to return a negative number, and
so `n == 1` is not a special case in the answer — only potentially in the code.

## 2. Constraint reading

| Constraint | What it rules in / out |
|---|---|
| `1 <= prices.length <= 10^5` | O(n²) is `10^10` pair evaluations — dead. O(n log n) would pass but is unnecessary. The target is **O(n) single pass**. Also: length can be **1**, so any code that reads `prices[1]` or does `for (i = 1; i < n; i++)` with an unguarded `prices[0]` seed must be checked. Length 0 is *excluded*, so `prices[0]` is always safe to read. |
| `0 <= prices[i] <= 10^4` | Non-negative, so `0` is a legal price and `Integer.MAX_VALUE` is a safe sentinel for "minimum so far". Max conceivable profit is `10^4 - 0 = 10^4` — no overflow anywhere, `int` is plenty. Small bounded range hints a counting/bucketing solution is *possible* but it buys nothing here. |
| Array, not stream | We may index freely and go backwards. But note the problem has a natural left-to-right causality (buy before sell) which strongly suggests a forward scan is the natural fit. |
| No "sorted" | Deliberately absent. Sorting would destroy the day ordering, which *is* the constraint. Any solution that sorts is wrong on its face. |
| One transaction only | This is the key restriction. LC122 (unlimited transactions) and LC123/188 (`k` transactions) are different problems with different answers; conflating them is the classic error. |

The signal I read overall: *linear scan, constant memory, one running extremum*.

## 3. Clarifying questions I would ask an interviewer

1. **Must the sell day be strictly after the buy day, or is same-day allowed?**
   → Assume strictly after (`j > i`). Immaterial to the answer since same-day profit is 0 and 0 is the floor.
2. **Exactly one transaction, or at most one?** → Assume *at most* one; "if you cannot achieve any profit, return 0" confirms declining is permitted. If it were *exactly* one forced transaction, the answer for `[7,6,4,3,1]` would be `-1`, not `0`.
3. **Do you want the profit only, or also the buy/sell days?** → Assume profit only; I will mention that tracking indices costs two extra variables and no extra asymptotic cost.
4. **Can prices be negative (e.g., a spread or a futures contract)?** → Constraints say no, but my solution should not *rely* on non-negativity. I will use `Integer.MAX_VALUE` as the seed rather than `0`, so the code stays correct for negative prices too.
5. **Is the array huge enough to stream (can't fit in memory)?** → Assume it fits. Worth volunteering that the optimal algorithm is online and needs O(1) state, so it streams for free.
6. **Ties — if multiple pairs give the max profit, any preference (earliest sell)?** → Assume no preference, we return only the number.

## 4. Brute force

**Idea.** The answer is a maximum over a set of candidate pairs. Enumerate the
set. For each buy day `i`, try every later sell day `j`, and keep the best
difference seen.

```java
static int maxProfitBrute(int[] prices) {
    int best = 0;
    for (int i = 0; i < prices.length; i++) {
        for (int j = i + 1; j < prices.length; j++) {
            best = Math.max(best, prices[j] - prices[i]);
        }
    }
    return best;
}
```

**Complexity.** Time `O(n²)` — the inner loop runs `n-1, n-2, …, 0` times, so
`n(n-1)/2` iterations. Space `O(1)`.

**Why it is unacceptable here.** With `n = 10^5`, `n(n-1)/2 ≈ 5·10^9`
subtractions. At a generous `10^9` simple ops/second that is seconds to tens of
seconds — an order of magnitude past any judge or interview bar. It is, however,
the right thing to *say first*: it establishes the definition of the answer and
gives me a reference implementation to diff against.

Note `best` is seeded at `0`, not `Integer.MIN_VALUE`. That single choice
implements the "return 0 if no profit" rule and makes `n == 1` (inner loop never
runs) automatically correct.

## 5. The chain of improvements

### Step 1 — observe the loops are asymmetric in what they need

**Observation.** In the inner loop, `prices[i]` is a constant. We compute
`prices[j] - prices[i]` for many `j`. Restructure: for a *fixed sell day* `j`,
the best profit is `prices[j] - min(prices[0..j-1])`. The inner maximisation
over `i` is really a *minimisation of the buy price* over the prefix.

**Consequence.** The answer factorises:

```
answer = max over j of ( prices[j] - min over i<j of prices[i] )
```

Two nested optimisations, but the inner one no longer depends on `j` except
through the *range* `[0, j)`.

### Step 2 — dead end: precompute prefix minima into an array

**Approach.** Build `prefMin[j] = min(prices[0..j-1])` in one pass, then answer
`= max(prices[j] - prefMin[j])` in a second pass.

```java
static int maxProfitPrefixArray(int[] prices) {
    int n = prices.length;
    int[] prefMin = new int[n];
    prefMin[0] = prices[0];
    for (int j = 1; j < n; j++) prefMin[j] = Math.min(prefMin[j - 1], prices[j - 1]);
    int best = 0;
    for (int j = 1; j < n; j++) best = Math.max(best, prices[j] - prefMin[j]);
    return best;
}
```

**Why I abandoned it.** It is already `O(n)` time — so it is *correct and fast
enough*. But it burns `O(n)` extra space for a value we consume immediately
after producing. That is a smell: `prefMin[j]` is only ever read at iteration
`j`. I keep this in my pocket as the honest stepping stone (it is the right
thing to write on a whiteboard if the one-pass version isn't obvious yet) but it
is not the destination.

### Step 3 — dead end: sort, or use a heap

**Approach.** "Maximum difference" smells like "max minus min", so: return
`max(prices) - min(prices)`.

**Why it is wrong.** It ignores order. On `[7,1,5,3,6,4]` it happens to give
`6 - 1 = 5`, which is right — dangerously right. On `[2, 1]` it gives `2 - 1 =
1`, but the true answer is `0`, because the max occurs *before* the min. Any
approach that discards the index ordering (sorting, a heap of all values, a
`TreeSet`) loses exactly the information the problem is about. Rejected — and I
will keep `[2,1]` as my go-to counterexample for this whole family of wrong
answers.

### Step 4 — dead end (well, a detour): divide and conquer

**Approach.** Split at the midpoint. The best pair is either entirely in the
left half, entirely in the right half, or straddles — and the straddling case is
`max(right) - min(left)`. Combine in `O(1)` after computing halves' min/max.

**Complexity.** `T(n) = 2T(n/2) + O(1)` → `O(n)` if min/max are returned up the
recursion, or `O(n log n)` if recomputed. So it is *not asymptotically better*
than the prefix scan, costs `O(log n)` stack, and is far more code. Rejected on
simplicity grounds. Worth naming aloud in an interview because it is the
maximum-subarray analogy, and it shows I see the structure.

### Step 5 — the collapse to one pass

**Observation.** In step 2's two passes, the first pass computes `prefMin` left
to right, and the second pass consumes it left to right. Two loops walking the
same direction over the same index, with no dependency of the first on the
second, can always be **fused** into one loop.

**Consequence.** Carry `minSoFar` as a scalar. At day `j`, before considering
`j` as a buy candidate, `minSoFar` already equals `min(prices[0..j-1])` — which
is precisely the legal buy window for selling on day `j`. So: score `j` as a
sell day *first*, then fold `j` into `minSoFar`. Order of those two statements
is the entire correctness argument, and getting it backwards is the classic bug
(it would permit buying and selling on the same day — harmless here, giving 0,
but wrong in spirit and fatal in variants).

`O(n)` time, `O(1)` space, one pass, online. That is the destination.

### Step 6 — the reframe that generalises (Kadane)

**Observation.** Define `d[i] = prices[i] - prices[i-1]`, the daily deltas. Then
`prices[j] - prices[i] = d[i+1] + d[i+2] + … + d[j]` — a *contiguous subarray
sum* of `d`. So this problem is exactly **maximum subarray sum** (Kadane) on the
delta array, with the empty subarray allowed (which is what the floor-at-0
does).

**Consequence.** Same `O(n)`/`O(1)`, no better. But it is the right lens for the
harder relatives (LC122, LC123, LC188, and "at most one transaction with a
cooldown"), and it explains *why* the greedy running-minimum works: it is a
disguised DP where the state "best profit ending here" needs only the previous
value. I will present the running-minimum form as primary and this as the
alternative framing.

## 6. Optimal approach

**Invariant.** At the top of the loop body for index `i` (for `i ≥ 1`):

- `minSoFar == min(prices[0 .. i-1])` — the cheapest legal buy price for a sale on day `i`;
- `best == max over all pairs (a, b) with a < b <= i-1 of (prices[b] - prices[a])`, floored at 0 — the answer restricted to the prefix `prices[0..i-1]`.

Both are re-established by the body: we first extend `best` with every pair
whose sell day is `i` (there is only one candidate worth checking, `prices[i] -
minSoFar`, because `minSoFar` is the best buy for that sell day), then extend
`minSoFar` with `prices[i]`. On exit `i == n`, so `best` is the answer for the
whole array.

```java
/**
 * Maximum profit from at most one buy followed by a later sell.
 * Time O(n), space O(1), single forward pass, online.
 */
static int maxProfit(int[] prices) {
    int minSoFar = Integer.MAX_VALUE; // cheapest price strictly before the current day
    int best = 0;                     // 0 = decline to trade; always achievable

    // Invariant, checked at the top of each iteration:
    //   minSoFar == min(prices[0..i-1])   (MAX_VALUE when i == 0)
    //   best     == answer for prices[0..i-1], floored at 0
    for (int price : prices) {
        // Score today as a SELL day, using only buys from strictly earlier days.
        // Guard against the i == 0 case where minSoFar is the sentinel.
        if (minSoFar != Integer.MAX_VALUE) {
            best = Math.max(best, price - minSoFar);
        }
        // Only now may today become a candidate BUY day for future sells.
        minSoFar = Math.min(minSoFar, price);
    }
    return best;
}
```

Two remarks on the shape.

- The sentinel guard is defensive, not strictly needed under the stated
  constraints: with `prices[i] >= 0`, `price - Integer.MAX_VALUE` underflows to
  a large *positive* int on the very first iteration, which would corrupt
  `best`. Concretely `0 - 2147483647 = -2147483647` (fine), but
  `7 - Integer.MAX_VALUE` wraps to `-2147483640` (also fine) — in fact for
  `price <= 10^4` the subtraction stays negative and no corruption occurs. I keep
  the guard anyway because it makes correctness independent of the value range,
  and because the alternative (seeding `minSoFar = prices[0]` and looping from
  index 1) is the version I would actually write. Both are below.
- The enhanced-for loop is deliberate: nothing in the algorithm needs the index,
  which is itself evidence the state is O(1).

**The version I would write on a whiteboard** — no sentinel, no guard, and the
`length >= 1` constraint makes `prices[0]` safe:

```java
static int maxProfit(int[] prices) {
    int minSoFar = prices[0];
    int best = 0;
    for (int i = 1; i < prices.length; i++) {
        best     = Math.max(best, prices[i] - minSoFar); // sell today
        minSoFar = Math.min(minSoFar, prices[i]);        // or buy today for later
    }
    return best;
}
```

For `n == 1` the loop body never executes and `best` is `0`. Correct.

**Kadane framing, for completeness:**

```java
static int maxProfitKadane(int[] prices) {
    int runningProfit = 0; // best profit of a transaction ending today, or 0
    int best = 0;
    for (int i = 1; i < prices.length; i++) {
        runningProfit = Math.max(0, runningProfit + prices[i] - prices[i - 1]);
        best = Math.max(best, runningProfit);
    }
    return best;
}
```

### Dry run — Example 1: `prices = [7,1,5,3,6,4]` (expected `5`)

Using the whiteboard version. State shown *before* the row's work, then after.

| `i` | `prices[i]` | `minSoFar` in | `prices[i] - minSoFar` | `best` out | `minSoFar` out | Note |
|---|---|---|---|---|---|---|
| — | — | — | — | 0 | 7 | init from `prices[0]` |
| 1 | 1 | 7 | -6 | 0 | 1 | selling at 1 is a loss; 1 becomes the new floor |
| 2 | 5 | 1 | 4 | **4** | 1 | first profitable pair (buy day 2, sell day 3) |
| 3 | 3 | 1 | 2 | 4 | 1 | worse than 4; 3 does not beat the floor of 1 |
| 4 | 6 | 1 | 5 | **5** | 1 | the answer — buy 1, sell 6 |
| 5 | 4 | 1 | 3 | 5 | 1 | dip at the end cannot help |

Return `5`. Matches.

### Dry run — Example 2: `prices = [7,6,4,3,1]` (expected `0`)

| `i` | `prices[i]` | `minSoFar` in | `prices[i] - minSoFar` | `best` out | `minSoFar` out |
|---|---|---|---|---|---|
| — | — | — | — | 0 | 7 |
| 1 | 6 | 7 | -1 | 0 | 6 |
| 2 | 4 | 6 | -2 | 0 | 4 |
| 3 | 3 | 4 | -1 | 0 | 3 |
| 4 | 1 | 3 | -2 | 0 | 1 |

Return `0`. Matches. Note every difference is negative, `best` never leaves its
seed, and `minSoFar` tracks the strictly decreasing sequence — this is exactly
the case the floor-at-0 seed exists to handle.

## 7. Complexity

**Time — `O(n)`.** The loop executes exactly `n - 1` times (or `n` in the
sentinel version). Each iteration does one subtraction, two comparisons, and at
most two assignments — all `O(1)`, with no hidden allocation and no nested
iteration. Total `c·n` for a small constant `c`. Reading the input is itself
`Ω(n)` because any unread element could change the answer (flip it to `10^4`
after the minimum, and the answer changes), so `O(n)` is optimal — see § 6 of
the answer pass for that argument written out.

**Space — `O(1)`.** Two `int` locals, `minSoFar` and `best`, regardless of `n`.
No recursion, so no stack growth. The prefix-array variant would be `O(n)`
auxiliary; fusing the loops is precisely what removed it.

**Numeric safety.** Values in `[0, 10^4]` bound any difference to
`[-10^4, 10^4]`, far inside `int`. No `long` needed, no overflow. The only place
overflow could appear is the `Integer.MAX_VALUE` sentinel subtraction, which the
guard removes.

## 8. Edge cases

| Case | Input | Why it is dangerous | What the code does |
|---|---|---|---|
| Single day | `[5]` | No valid `(i, j)` pair exists at all; an unguarded `prices[1]` read throws; a `MIN_VALUE` seed would return garbage | Loop body never runs; returns `0` (seed). Correct |
| Two days, rising | `[1, 5]` | Smallest input with a real answer; off-by-one in the loop bound silently returns 0 | `i = 1`: `5 - 1 = 4` → returns `4` |
| Two days, falling | `[2, 1]` | Kills every "max minus min" solution, which returns `1` | `i = 1`: `1 - 2 = -1`, `best` stays `0` → returns `0` |
| Strictly decreasing | `[7,6,4,3,1]` | Answer is `0`; a `MIN_VALUE`-seeded `best` returns `-1` | Returns `0` (Example 2) |
| Strictly increasing | `[1,2,3,4,5]` | Answer must be `last - first`, not a sum of daily gains (`4`, not `4`… but for LC122 it would be `4` vs `4` — the trap is real on other inputs) | `minSoFar` pins at `1`, `best` climbs to `4`. Correct |
| All equal | `[3,3,3,3]` | Off-by-one or `>=` vs `>` confusion could yield a spurious `0`-profit "trade" or a negative | Every difference is `0`; returns `0` |
| Global max before global min | `[9,1]`, or `[5,9,1,2]` | The naive `max - min` gives `8` / `8`; the ordering constraint is the whole point | `[5,9,1,2]`: best `= 9-5 = 4`, then `2-1 = 1` → returns `4` |
| Minimum is the last element | `[4,3,2,1,0]` | The best buy price is discovered too late to ever be used | `minSoFar` updates but is never profitably consumed; returns `0` |
| Zero prices | `[0, 0]`, `[0, 10000]` | `0` is a legal price, so `0` is a bad "unset" sentinel for `minSoFar` | Returns `0` and `10000`. The `MAX_VALUE`/`prices[0]` seed avoids the trap |
| Max spread | `[0, 10000]` | Confirms no overflow and the answer bound | Returns `10000` |
| Same-day buy/sell | any | If the update order is flipped (`minSoFar` before scoring), day `i` can buy *and* sell from itself | Scoring happens **before** the `minSoFar` update, so day `i` can only buy from `[0, i-1]`. Invariant holds |
| Large `n` | `10^5` elements | Rules out `O(n²)` | Single pass, ~`10^5` iterations. Trivial |
| Input mutation | any | Callers may reuse the array | Read-only; never assigns into `prices` |

## 9. How I would present this in an interview

> "Let me restate it: one buy, one later sell, maximise the difference, and if
> every pair loses money I return 0 — so declining to trade is always an option.
> Two quick clarifications: sell must be strictly after buy, yes? And it's *at
> most* one transaction, not a forced one — the return-0 rule implies that.
>
> Brute force is the definition: for every buy day, try every later sell day,
> keep the max. `O(n²)` time, `O(1)` space. With `n` up to `10^5` that's about
> five billion operations, so it won't pass — but it pins down what the answer
> means.
>
> The bottleneck is that the inner loop recomputes something stale. Flip the
> loop around: fix the *sell* day `j`. The best profit selling on day `j` is
> `prices[j]` minus the cheapest price *before* `j`. So the answer is the max
> over `j` of `prices[j] - prefixMin(j)`. That's still two passes if I
> materialise the prefix minima into an array, but both passes walk left to
> right, so I can fuse them and carry the minimum in a single scalar.
>
> One pass: keep `minSoFar` and `best`. For each day, first score today as a
> sell against `minSoFar`, *then* fold today into `minSoFar`. That order is the
> correctness argument — it guarantees the buy day is strictly earlier than the
> sell day. The invariant is: entering iteration `i`, `minSoFar` is the min of
> `prices[0..i-1]` and `best` is the answer for the prefix `prices[0..i-1]`.
> Seed `best = 0` and that handles the no-profit case and the length-1 case for
> free.
>
> `O(n)` time, `O(1)` space. `O(n)` is a lower bound because any element I skip
> could be the answer, so this is optimal. It's also online — one pass, constant
> state — so it works on a stream.
>
> Let me test it. `[7,1,5,3,6,4]`: min goes 7, 1 and stays; best goes 0, 4, 5 —
> returns 5. `[7,6,4,3,1]`: every difference is negative, returns 0. `[2,1]`
> returns 0 — that's the case that kills the naive `max - min` answer. `[5]`
> returns 0, loop never runs.
>
> One framing worth mentioning: if I take daily deltas, `prices[j] - prices[i]`
> is a contiguous subarray sum, so this is exactly maximum-subarray / Kadane
> with the empty subarray allowed. Same complexity, but that's the lens that
> generalises to the multi-transaction and `k`-transaction versions."

Roughly 60–75 seconds. Order is fixed: clarify → brute force → bottleneck →
optimal + invariant → complexity + optimality → test → generalisation.

## 10. Pattern name

**Family.** Single-pass running-extremum scan (prefix-aggregate / "best pair
with an ordering constraint"). Equivalently: one-dimensional DP with O(1) state,
or Kadane on the difference array.

**Trigger.** *If the answer is the best `f(a[j], a[i])` over pairs with `i < j`,
and `f` decomposes so that the optimal `i` for a given `j` depends only on a
running aggregate of the prefix `a[0..j-1]` → fix the later index, carry that
aggregate in a scalar, and update it strictly after scoring the current index.*

Shorter, interview-recall form: **"maximum difference with a before-after
constraint → one pass, track the running minimum, score before you update."**
