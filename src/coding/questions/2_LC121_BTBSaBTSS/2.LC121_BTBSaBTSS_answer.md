## 3. Remaining defects

None in correctness. Three in robustness and precision — all worth internalising
because each one is a near miss rather than a bug.

### Defect 1 — two risky choices that happen to cancel

Your optimal code:

```java
int mx = Integer.MIN_VALUE;          // (a) seeded negative, not 0

for (int price : prices) {
    if (price < min_pr) min_pr = price;   // (b) min updated FIRST
    if (price - min_pr > mx) mx = price - min_pr;
}
return mx;                            // (c) returned unfloored
```

Choices (a) and (c) together say "I might return a negative number". Choice (b)
says "today is allowed to be both the buy day and the sell day". Individually,
each is a smell. Together they cancel exactly:

Because the minimum is folded in *before* the profit is scored, `min_pr <= price`
holds unconditionally at the scoring line, so `price - min_pr >= 0` always. On
the very first iteration that expression is exactly `0`, so `mx` is lifted from
`Integer.MIN_VALUE` to `0` immediately and can never go below it. The unfloored
return is therefore safe — but only because of (b).

**Now swap the two `if` blocks** and change nothing else:

```java
if (price - min_pr > mx) mx = price - min_pr;   // score first
if (price < min_pr) min_pr = price;             // then update
```

This ordering is the one *I* would call more correct in spirit — it enforces
buy-strictly-before-sell rather than relying on the same-day profit being zero.
But with your seeds it breaks. Trace `[7,6,4,3,1]`:

| iter | `price` | `min_pr` in | `price - min_pr` | `mx` out | `min_pr` out |
|---|---|---|---|---|---|
| 1 | 7 | `2147483647` | `7 - 2147483647` = `-2147483640` | `-2147483640` | 7 |
| 2 | 6 | 7 | -1 | -1 | 6 |
| 3 | 4 | 6 | -2 | -1 | 4 |
| 4 | 3 | 4 | -1 | -1 | 3 |
| 5 | 1 | 3 | -2 | -1 | 1 |

Returns `-1`. Expected `0`.

So your submission is correct, and a one-line reordering that a reviewer might
reasonably suggest as a *cleanup* would break it. That is the practical cost of
not writing the invariant: you cannot see which of your lines are load-bearing.
**Fix:** seed `mx = 0`. Then both orderings are correct and the code stops being
a house of cards. `0` is the honest seed because declining to trade is a real,
always-available outcome — not a sentinel.

### Defect 2 — "local minimum" is the wrong term

You wrote:

> "We track the local minimum and compare it with next numbers till we see next
> minimum."

A **local minimum** is a valley: an element smaller than both its neighbours.
`[3, 2, 6, 5, 0, 3]` has local minima at `2` and `0`. That is not what your
variable holds. `min_pr` holds the **prefix minimum** — the minimum of everything
seen so far — which is a *monotone non-increasing* sequence: `3, 2, 2, 2, 0, 0`.
The distinction is not pedantic. A local minimum can go back up; a prefix minimum
never does, and that monotonicity is a large part of why the scan is correct
(you never need to reconsider a buy price you have walked past). Say "running
minimum" or "prefix minimum".

### Defect 3 — the brute force is `j = i`, not `j = i + 1`

```java
for (int j = i; j < n; j++)
```

`j == i` means buying and selling on the same day, which the problem forbids
("a different day in the future"). It is harmless — the pair contributes `0`,
and `0` is the floor anyway, so the returned value is unaffected — but you should
know you did it and be able to say why it does not matter. If the problem were
"exactly one transaction, profit may be negative", that single character would be
the bug. Write `j = i + 1` and seed `best = 0`; then the loop bounds encode the
rule and the seed encodes the opt-out, each doing one job.

Also: `Math.max(mx, 0)` at the end of the brute force is dead code given
`j = i` — `mx` is already `>= 0`. Two mechanisms for the same guarantee is one
too many.

## 4. The correct answer

### 4.1 Brute force

The answer is a maximum over a finite set of candidate pairs, so enumerate the
set. This is not an algorithm so much as a restatement of the problem — which is
exactly its value: it *defines* the answer, and it is the reference you diff
every optimisation against.

```java
/** Maximum profit from at most one buy followed by a strictly later sell. */
static int maxProfitBrute(int[] prices) {
    int best = 0;                                    // 0 = decline to trade
    for (int i = 0; i < prices.length; i++) {
        for (int j = i + 1; j < prices.length; j++) { // j > i enforces buy-before-sell
            best = Math.max(best, prices[j] - prices[i]);
        }
    }
    return best;
}
```

**Complexity.** The inner loop runs `n-1, n-2, …, 1, 0` times, summing to
`n(n-1)/2` — your triangular-matrix observation, stated as a number. So time is
`O(n²)` and space is `O(1)`.

**Why it fails here.** `n = 10^5` gives `10^5 · (10^5 - 1) / 2 ≈ 5 × 10^9`
subtract-and-compare pairs. At an optimistic `10^9` simple operations per second
that is roughly 5 seconds of pure arithmetic, against a typical 1–2 second
budget. It is off by about an order of magnitude, which is the interesting kind
of "too slow" — not absurd, just clearly out.

Note `best = 0`: that single choice implements the "return 0 if no profit" rule
and makes `n == 1` correct for free, because the inner loop never runs.

### 4.2 The bottleneck, and the derivation

This is the sentence item 4 asked for:

> **The inner loop recomputes, for every sell day `j`, a search over buy days
> that overlaps almost entirely with the search it already did for `j - 1`.**

Unpack it. Rearrange the brute force so the *outer* loop is the sell day:

```
answer = max over j of ( max over i < j of ( prices[j] - prices[i] ) )
```

For a fixed `j`, `prices[j]` is a constant, so maximising `prices[j] - prices[i]`
over `i` is the same as **minimising `prices[i]`** over `i < j`. The inner
maximisation collapses:

```
answer = max over j of ( prices[j] - min(prices[0 .. j-1]) )
```

Two things follow immediately.

1. Each sell day has exactly **one** buy candidate worth checking — the cheapest
   day before it. Every other buy day is dominated. That kills the inner loop's
   `O(n)` search and replaces it with a lookup.
2. `min(prices[0..j-1])` for consecutive `j` differ by one element. It does not
   need recomputing; it can be **maintained** in a scalar:
   `min(prices[0..j]) = min( min(prices[0..j-1]), prices[j] )`.

Point 1 alone gets you a correct two-pass, `O(n)`-time, `O(n)`-space solution
(materialise the prefix minima into an array — § 5, approach B). Point 2 fuses
the two passes, because both walk left to right and the second only ever reads
the value the first just produced. That fusion is the whole optimisation, and
`O(n)` space becomes `O(1)`.

### 4.3 Why it works — the invariant and the name

This is the part you asked for. Three framings of the same fact, in increasing
order of generality. Learn the first, recognise the second, and keep the third
for the harder relatives.

#### Framing 1 — the loop invariant (this is the proof)

State it as a property that is true *at the top of every iteration*, before the
body runs. Let `i` be the index about to be processed:

```
minSoFar == min(prices[0 .. i-1])
best     == the answer for the sub-array prices[0 .. i-1], floored at 0
```

Note the ranges. Both end at `i - 1`, **excluding** the current element. That
exclusion is the buy-before-sell rule, encoded as an index range.

Three obligations discharge the proof:

- **Initialisation.** Before the first iteration, `i = 0`, so both ranges are
  empty. `minSoFar` is `+∞` (min of nothing) and `best` is `0` (the answer over
  an empty array — no pairs exist, so decline to trade). Both hold.
- **Maintenance.** The body must re-establish the invariant with `i` incremented.
  Consider every pair whose sell day is exactly `i`. Its buy day is some `a < i`,
  and the best such pair is `prices[i] - min(prices[0..i-1])` = `prices[i] -
  minSoFar`, by the invariant. So `best = max(best, prices[i] - minSoFar)`
  extends `best` from "answer over `[0, i-1]`" to "answer over `[0, i]`" —
  because every pair in the larger range either lived in the smaller range
  (already counted) or sells on day `i` (just counted). Then
  `minSoFar = min(minSoFar, prices[i])` extends the minimum from `[0, i-1]` to
  `[0, i]`. Both clauses now hold for `i + 1`.
- **Termination.** The loop exits with `i == n`, so `best` is the answer over
  `prices[0 .. n-1]` — the whole array. Done.

That is a complete correctness proof and it fits in a paragraph. It is what you
say out loud when the interviewer asks "why does that work?".

**The update order falls straight out of the invariant.** `best` is scored
against `minSoFar` *while* `minSoFar` still means "min over `[0, i-1]`". Fold
`prices[i]` in first and `minSoFar` means "min over `[0, i]`", which permits
`a == i` — buying and selling on the same day. Here that is benign (it
contributes exactly `0`, and `0` is the floor) but it is benign by accident, not
by design, and it is fatal the moment the problem adds a cooldown, a transaction
fee, or a "must hold at least `k` days" clause. Score first, update second.

#### Framing 2 — dynamic programming with collapsed state

Define `f(i)` = the best profit of a transaction whose **sell day is exactly `i`**
(or `0` if no sale on day `i` is profitable). Then:

```
f(i) = max(0, prices[i] - min(prices[0..i-1]))
answer = max over i of f(i)
```

This is a one-dimensional DP. The usual DP artefact would be an array `f[]` of
size `n`, but `f(i)` depends on the prefix only through a single scalar — the
running minimum — and `f(i)` itself is consumed immediately by the running
maximum. So both the table and the state collapse to two `int`s. That collapse
is the general move: **when a DP's state is a scalar aggregate of the prefix, the
table disappears and the DP becomes a single scan.**

Standard name for the sub-idea: **prefix aggregate** / **running extremum**. The
family is "best pair `(i, j)` with `i < j` under an order constraint": fix the
later index, carry the aggregate of everything before it.

#### Framing 3 — Kadane, i.e. "best profit ending here"

Take daily deltas: `d[k] = prices[k] - prices[k-1]` for `k >= 1`. Then

```
prices[j] - prices[i] = d[i+1] + d[i+2] + … + d[j]
```

— a **contiguous subarray sum** of `d`. So LC121 is *literally* maximum subarray
sum on the delta array, with the empty subarray allowed (which is precisely what
flooring at `0` means).

Kadane's algorithm carries `endingHere` = the best subarray sum ending at the
current index, updated as `endingHere = max(0, endingHere + d[k])`. Translated
back into stock terms, `endingHere` is **the best profit of a transaction that
sells today**, and the `max(0, …)` is "if my running position is underwater,
abandon it and re-buy at today's price". Abandoning a losing position and
re-buying is *exactly* what "update the running minimum" does. The two algorithms
are the same algorithm in different coordinates:

| Running-minimum form | Kadane-on-deltas form |
|---|---|
| `minSoFar` | the buy price implied by the current open position |
| `prices[i] - minSoFar` | `endingHere` |
| "`prices[i]` is a new minimum, reset the buy" | "`endingHere` went negative, reset to 0" |
| `best = max(best, …)` | `best = max(best, endingHere)` |

```java
static int maxProfitKadane(int[] prices) {
    int endingHere = 0; // best profit of a transaction that sells TODAY, or 0
    int best = 0;
    for (int i = 1; i < prices.length; i++) {
        endingHere = Math.max(0, endingHere + prices[i] - prices[i - 1]);
        best = Math.max(best, endingHere);
    }
    return best;
}
```

**Why bother with framing 3 when framing 1 already proves it?** Because it is the
one that generalises. LC122 (unlimited transactions), LC123 (at most two), LC188
(at most `k`), LC309 (cooldown), LC714 (fee) are all "best profit ending here"
DPs with more states. The running-minimum trick does not extend to them; the
`endingHere` framing does. Mention framing 3 in an interview *after* you have
delivered framing 1 — it signals you see the family, not just the instance.

**So: the name of the thing you wrote** is a *single-pass prefix-minimum scan*,
a.k.a. one-dimensional DP with `O(1)` state, a.k.a. Kadane on the difference
array. All three are the same code.

### 4.4 The optimal solution

```java
/**
 * Maximum profit from at most one buy followed by a strictly later sell.
 * Time O(n), space O(1). Single forward pass, online (works on a stream).
 */
static int maxProfit(int[] prices) {
    int minSoFar = prices[0]; // length >= 1 is guaranteed, so this read is safe
    int best = 0;             // 0 is a real answer: decline to trade

    // INVARIANT, true at the top of every iteration:
    //   minSoFar == min(prices[0 .. i-1])
    //   best     == answer for prices[0 .. i-1], floored at 0
    for (int i = 1; i < prices.length; i++) {
        // Score today as a SELL day. Valid because minSoFar still excludes i,
        // so the implied buy day is strictly earlier. This line MUST precede
        // the next one.
        best = Math.max(best, prices[i] - minSoFar);
        // Only now may today become a candidate BUY day for future sells.
        minSoFar = Math.min(minSoFar, prices[i]);
    }
    return best;
}
```

Seeding from `prices[0]` and starting at `i = 1` is preferable to the
`Integer.MAX_VALUE` sentinel: it removes the sentinel branch from the hot loop
and removes any question about `prices[i] - Integer.MAX_VALUE` underflowing. The
`length >= 1` constraint makes `prices[0]` safe; if you cannot rely on that, add
`if (prices == null || prices.length < 2) return 0;` as a guard and say so.

Sentinel variant, for when you would rather not special-case the seed:

```java
static int maxProfitSentinel(int[] prices) {
    int minSoFar = Integer.MAX_VALUE;
    int best = 0;
    for (int price : prices) {
        best = Math.max(best, price - minSoFar); // safe: see note
        minSoFar = Math.min(minSoFar, price);
    }
    return best;
}
```

The note: on the first iteration `price - Integer.MAX_VALUE` is a huge negative
number for any `price <= 10^4`, so `best` stays `0`. It does **not** overflow for
the given range (`0 - 2147483647 = -2147483647`, still in `int`). It *would*
overflow if prices could be negative — `-2 - Integer.MAX_VALUE` wraps to a large
positive value and corrupts `best`. Prefer the `prices[0]` seed.

### 4.9 Complexity

**Time — `Θ(n)`.** The loop runs exactly `n - 1` times. Each iteration performs
one subtraction, two comparisons, and at most two register assignments — all
`O(1)`, no allocation, no nested iteration, no hidden `Math` cost (`Math.max` on
`int` is intrinsified to a compare-and-move). Total work is `c·n` for a small
constant `c`. Not amortised, not average-case: exactly linear on every input.

**Space — `O(1)`.** Two `int` locals regardless of `n`. No recursion, so no stack
growth. The prefix-min array version would be `O(n)` auxiliary; fusing the two
passes is precisely the step that removed it.

**Numeric safety.** With `0 <= prices[i] <= 10^4`, any difference lies in
`[-10^4, 10^4]`, comfortably inside `int`. No `long`, no overflow — provided you
avoid the `Integer.MAX_VALUE` sentinel subtraction (§ 4.4).

## 5. Alternative correct solutions

**A — Brute force.** § 4.1. `O(n²)` / `O(1)`.

**B — Prefix-minimum array, two passes.** The honest stepping stone; correct and
fast enough, just wasteful.

```java
static int maxProfitPrefixArray(int[] prices) {
    int n = prices.length;
    int[] prefMin = new int[n];
    prefMin[0] = prices[0];
    for (int j = 1; j < n; j++) prefMin[j] = Math.min(prefMin[j - 1], prices[j - 1]);
    int best = 0;
    for (int j = 1; j < n; j++) best = Math.max(best, prices[j] - prefMin[j]);
    return best;
}
```

**C — Suffix-maximum array.** The mirror image: fix the *buy* day and precompute
`sufMax[i] = max(prices[i+1..n-1])` right to left, then answer
`max(sufMax[i] - prices[i])`. Equally correct, `O(n)`/`O(n)`, but it cannot be
fused into a single forward pass because the second loop would need to run
backwards. Worth knowing that the problem is symmetric, and worth knowing why
only one of the two directions collapses to `O(1)` space.

**D — Divide and conquer.** Split at the midpoint. The optimal pair lies entirely
left, entirely right, or straddles — and the straddling case is
`max(right half) − min(left half)`. Return `(min, max, best)` up the recursion
and the combine is `O(1)`, giving `T(n) = 2T(n/2) + O(1) = O(n)`. If you
recompute the halves' min/max instead, it degrades to `O(n log n)`. Costs
`O(log n)` stack and far more code for no asymptotic gain — but it is the same
recursion as maximum-subarray, so naming it shows you see the structure.

**E — Kadane on the delta array.** § 4.3, framing 3. `O(n)`/`O(1)`.

**F — Single-pass running minimum.** § 4.4. The destination.

| Approach | Time | Space | Passes | In-place / read-only | Online? | When it wins |
|---|---|---|---|---|---|---|
| A brute force | `O(n²)` | `O(1)` | — | read-only | no | `n <= ~2000`; as the definition you diff against |
| B prefix-min array | `O(n)` | `O(n)` | 2 | read-only | no | When you need the prefix minima for other queries too |
| C suffix-max array | `O(n)` | `O(n)` | 2 | read-only | no | When the natural framing is "fix the buy day" |
| D divide & conquer | `O(n)` | `O(log n)` | 1 | read-only | no | Parallel/fork-join over a huge array; range queries via a segment tree |
| E Kadane on deltas | `O(n)` | `O(1)` | 1 | read-only | yes | When you must generalise to `k` transactions, fees, or cooldowns |
| **F running minimum** | `O(n)` | `O(1)` | 1 | read-only | **yes** | Default. Fewest branches, no allocation, streams for free |

F and E compile to near-identical machine code. F has a marginal edge: it reads
`prices[i]` once per iteration where E reads `prices[i]` and `prices[i-1]`.

**Not a solution: sorting.** `Arrays.sort(prices)` then `last − first` destroys
the day ordering, which *is* the constraint. `O(n log n)` and wrong. Any approach
whose output is invariant under permutation of the input is wrong on its face —
that is the Hint-1 test (item 1) you did not write down, and it disposes of an
entire family of wrong answers in one sentence.

## 6. Why the optimal is optimal

`O(n)` time is a genuine **lower bound**, provable by an adversary argument, not
merely best-known.

Suppose an algorithm returns the correct answer after reading strictly fewer than
`n` elements. Then some index `k` was never read. The adversary now names two
inputs that agree on every position the algorithm read and differ only at `k`:
one where `prices[k] = 0` and one where `prices[k] = 10^4`. Choose `k` in the
interior with a `10^4` somewhere after it and a `0` nowhere before it, and the
two inputs have different answers. The algorithm produced the same output for
both (it never distinguished them), so it is wrong on at least one. Therefore
every correct algorithm must read all `n` elements, and reading `n` elements is
`Ω(n)`. Our algorithm is `Θ(n)`. Matching bounds — optimal.

`O(1)` space is also optimal in the trivial sense: you cannot use less than
constant auxiliary space, and the algorithm does not modify the input.

There is nothing left to improve asymptotically. The only remaining axis is
constant factors — one branch fewer per iteration, or SIMD/vectorised
prefix-minimum on very large arrays — which is not what an interview is asking
about.

## 7. Interview delivery script

Say this, in this order. Roughly 70 seconds before you write any code.

> "Let me restate it. One buy, one strictly later sell, maximise the difference,
> and if every pair loses money I return 0 — so declining to trade is always
> available. Two clarifications: sell has to be strictly after buy, correct? And
> it's *at most* one transaction, not a forced one — the return-0 rule implies
> that, otherwise `[7,6,4,3,1]` would be `−1`.
>
> Constraints: `n` up to `10^5`, prices in `[0, 10^4]`. `10^5` rules out
> quadratic, and the bounded values mean `int` is safe with no overflow. Note `0`
> is a legal price, so I can't use `0` as an 'unset' sentinel.
>
> Brute force first, because it defines the answer: for every buy day, try every
> later sell day, keep the maximum. That's `n(n−1)/2` pairs — `O(n²)` time,
> `O(1)` space. At `n = 10^5` that's about five billion operations, several
> seconds. Too slow, but now I know what the answer *means*.
>
> The bottleneck: for each sell day the inner loop re-searches buy days it
> already searched for the previous sell day. So flip the loops — fix the sell
> day `j`. `prices[j]` is then a constant, so maximising the profit means
> *minimising* the buy price over days before `j`. Every buy day except the
> cheapest one is dominated. So the answer is `max over j of prices[j] minus the
> minimum of the prefix before j`.
>
> That's already `O(n)` if I materialise the prefix minima into an array. But
> both passes walk left to right and the second only reads what the first just
> wrote, so I can fuse them and carry the minimum in a single scalar.
>
> One pass, two variables. Invariant, at the top of iteration `i`: `minSoFar` is
> the minimum of `prices[0..i−1]`, and `best` is the answer for the prefix
> `prices[0..i−1]`, floored at 0. Body: first score today as a sell day against
> `minSoFar`, *then* fold today into `minSoFar`. That order is the correctness
> argument — scoring while `minSoFar` still excludes today is what guarantees
> the buy day is strictly earlier. Seed `best = 0` and the no-profit case and the
> length-1 case both fall out for free.
>
> `O(n)` time, `O(1)` space. `O(n)` is a lower bound — any element I skip could
> be flipped to change the answer — so this is optimal, not just fast. It's also
> online: constant state, one pass, so it runs on a stream.
>
> Let me test it. `[7,1,5,3,6,4]`: min goes 7 then 1 and pins; best goes 0, 4, 5
> — returns 5. `[7,6,4,3,1]`: every difference negative, returns 0. `[2,1]`
> returns 0, which is the case that kills the naive max-minus-min answer. `[5]`:
> loop never runs, returns 0.
>
> One framing worth naming: if I take daily deltas, `prices[j] − prices[i]` is a
> contiguous subarray sum, so this is exactly maximum-subarray — Kadane — with
> the empty subarray allowed. Same complexity here, but that's the lens that
> generalises to the multi-transaction, `k`-transaction, fee, and cooldown
> variants."

The two sentences that would have changed your grade, if you take nothing else:
**"the invariant is …"** and **"`O(n)` time, `O(1)` space, and `O(n)` is a lower
bound because …"**. Neither takes ten seconds to say.

## 8. Common wrong answers

**W1 — `max(prices) − min(prices)`.** The most common. Order-blind: its output
depends only on the multiset of values, so it cannot distinguish `[1,2]` from
`[2,1]`. **Killed by `[2,1]`** — returns `1`, answer is `0`. Also killed by
`[3,2,6,5,0,3]` — returns `6`, answer is `4`. This is the family attempt 1 fell
into, and the "let both pointers sweep the whole array" repair lands you here,
which is why the evaluation told you not to attempt it.

**W2 — converging two pointers from both ends.** Attempt 1. Fails for two
independent reasons: it never examines every element as both a candidate buy and
a candidate sell, and even with full coverage it degenerates into W1. The
diagnostic: a converging two-pointer scan is only valid when moving a pointer
inward is a *provably safe discard*. Here the pair is asymmetric — buy must
precede sell — so there is no discard argument for moving the right pointer left.
**Killed by `[3,2,6,5,0,3]`** — returns `3`, answer is `4`.

**W3 — sum every positive daily delta.** `for i: if (p[i] > p[i-1]) profit +=
p[i] - p[i-1]`. This is the correct answer to **LC122** (unlimited transactions),
not LC121. **Killed by `[1,5,1,5]`** — returns `8` (two round trips), answer is
`4` (one transaction only). It also fails Example 1: `[7,1,5,3,6,4]` gives
`(5−1) + (6−3) = 7`, not `5`. But on any *monotone* input it agrees with the
right answer (`[1,2,3,4,5]` → `4` both ways), so it survives casual testing.
Always test a multi-peak input.

**W4 — `MIN_VALUE`-seeded best, scored before the min update.** Defect 1. Two
locally reasonable choices that are incompatible. **Killed by `[7,6,4,3,1]`** —
returns `−1`, answer is `0`. Seed the best at `0` and the failure mode
disappears.

**W5 — track the first local minimum and the following local maximum.** "Buy at
the first valley, sell at the next peak." **Killed by `[4,1,2,9]`**… which it
actually gets right; the real killer is `[1, 2, 0, 100]` — it buys at the valley
`1`, sells at the peak `2`, returns `1`, while the answer is `100` (buy the later
valley `0`). A *local* minimum is not a *prefix* minimum, and only the prefix
minimum is the right thing to carry. This is defect 2, promoted from a
terminology slip to an actual bug.
