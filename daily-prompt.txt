  § 2. Theory Block — ONE per theory topic for the day
     For EACH theory topic, include ALL of the following sub-sections,
     even if it makes the section long:

     2.1 Origin & Motivation [BOTH]
         - Why does this concept exist? What problem in the field motivated
           its invention? Cite the paper / RFC / standard if applicable.
         - The historical alternative it replaced or extended.

     2.2 Intuition [BOTH]
         - The 30-second explanation someone could give a smart non-expert.
         - Concrete real-world analogy when helpful.

     2.3 Formal Definition [BOTH]
         - Precise definition. Math notation acceptable when needed.
         - Invariants, contracts, guarantees.

     2.4 Mechanics — How It Actually Works [BOTH]
         - Step-by-step internal operation.
         - For algorithms: pseudocode + worked example.
         - For data structures: memory layout, growth, deletion strategy.
         - For JVM features: bytecode, JIT behaviour, GC interaction.
         - For Spring features: filter/bean lifecycle, proxy mechanism.
         - For systems: state diagrams, protocol exchanges, write paths.

     2.5 Complexity / Cost Model [BOTH]
         - Time AND space, average AND worst case.
         - Concrete numbers at n = 10⁶ (or appropriate scale).
         - Constant-factor discussion (cache locality, allocation overhead).

     2.6 Implementation Walkthrough [BOTH]
         - Idiomatic Java 21 reference implementation, line-commented where
           non-obvious.
         - Common variants and their trade-offs.

     2.7 Edge Cases & Pitfalls [BOTH]
         - Off-by-one regions, empty input, single-element input, max
           values, negative numbers, Unicode, threading.
         - Each edge case as a bullet with a one-line explanation.

     2.8 Internals — One Layer Deeper [STAFF]
         - For algorithms: invariant proofs, amortized analysis, lower
           bounds, why this is optimal (or not).
         - For Java: bytecode, JIT, escape analysis, GC card tables, safepoints.
         - For data structures: cache effects, branch prediction, false
           sharing, allocation pressure.
         - For systems: replication protocols, failure detectors, clock skew.

     2.9 Real-World Failure Case Studies [STAFF]
         - At least one named real incident, postmortem, or production bug
           that involved this concept. Cite a blog post or postmortem when
           available.
         - What went wrong, root cause, what the fix taught the industry.

     2.10 Alternatives — When NOT to use this [BOTH + STAFF extension]
         - Other approaches in the design space.
         - Decision criteria (input size, latency profile, ops complexity,
           vendor lock-in).
         - 3-axis trade-off statement [STAFF].

     2.11 Connection to the Three Portfolio Projects [BOTH]
         - If/where this concept lands in Project 1 / 2 / 3.
         - If this is purely interview-theoretical, say so explicitly.

     2.12 Connection to the Real World [STAFF]
         - Where does this show up in production at scale? Name companies
           and systems. (Netflix, Uber, Discord, AWS, Stripe etc.)

     2.13 Common Misconceptions [BOTH]
         - 3–5 wrong beliefs that interviewers test you on.

     2.14 Interview Framing [BOTH]
         - How to introduce this in an interview answer.
         - What signal you give by handling it well.
         - What anti-signals juniors emit (so you can avoid).

     2.15 Further Reading [BOTH]
         - Inline links at point of mention AND collected here.

  § 3. Problem Block — ONE per problem for the day
     For EACH problem, include ALL of the following, exhaustively:

     3.1 Problem Statement [BOTH]
         - Paraphrased — do not copy-paste copyrighted LeetCode text.
         - LeetCode URL and NeetCode URL.
         - Frequency / company tags (which FAANG actually asks this).
         - Difficulty: Easy / Medium / Hard.

     3.2 Clarifying Questions [BOTH]
         - The exact questions you would ask the interviewer before coding.
         - Why each question matters.

     3.3 Brute Force [BOTH]
         - Always include the brute-force solution first.
         - Complexity analysis (time + space).
         - Why this is suboptimal (which constraint forces a better solution).

     3.4 Intermediate Improvements [BOTH]
         - Any in-between solutions (e.g., O(n²) → O(n log n) → O(n)).
         - State the algorithmic insight that unlocks each step.

     3.5 Optimal Solution(s) [BOTH]
         - Full idiomatic Java 21 implementation.
         - Line-by-line commentary for the non-obvious lines.
         - Alternative optimal implementations if multiple exist
           (heap vs bucket; iterative vs recursive; in-place vs auxiliary).

     3.6 Worked Trace [BOTH]
         - Walk through ONE small concrete example step by step.
         - Show variable state at each iteration.
         - For DP: show the table being filled.
         - For graphs: show the visited set / queue progression.

     3.7 Complexity Analysis [BOTH]
         - Time AND space, with justification (not just "O(n) trust me").
         - For amortized: explain the amortization.

     3.8 Edge Cases [BOTH]
         - List at least 5 edge cases and what your solution does on each.
         - Empty, single element, all duplicates, very large input, overflow,
           negative numbers, Unicode (where applicable), null inputs.

     3.9 Common Bugs [BOTH]
         - Off-by-one, exclusive vs inclusive bounds, integer overflow,
           autoboxing surprises, modifying collection while iterating,
           hashCode/equals omission for custom keys.

     3.10 Pattern Recognition [BOTH]
         - What signal in the problem statement says "this is pattern X."
         - List of related problems that share the pattern.

     3.11 Multi-Solution Comparison Table [BOTH]
         - Tabular comparison: approach | time | space | trade-off.

     3.12 Follow-Up Questions [BOTH]
         - The 3–5 follow-ups an interviewer is likely to ask.
         - Drafted answers for each.

     3.13 Scale-Up Addendum [STAFF]
         - What changes at 1B inputs?
         - Streaming variant (Count-Min Sketch, Bloom filter, reservoir
           sampling, sliding window, etc.).
         - Distributed variant (shard key, MapReduce shape, hot-shard risk).
         - Memory-bounded variant (external sort, disk-backed hash, mmap).

     3.14 Real-World Analogue [STAFF]
         - Where does this problem show up in production?
         - Example: Two Sum → join algorithm in databases; Top K Frequent →
           trending topics; LRU Cache → page replacement, CDN; etc.

     3.15 Trade-Off Drill [STAFF]
         - At least TWO framed "when A vs B?" questions with full 3-axis
           answers.

     3.16 Junior vs Senior vs Staff Lens [BOTH]
         - What a Junior would do wrong.
         - What a Senior IC says right.
         - What a Staff candidate adds on top.

     3.17 Interview Communication Script [BOTH]
         - The exact sentences to say while solving (clarifying → brute →
           optimal → complexity → edge cases → "anything you want me to
           optimize further?").

  WRITING RULES (fixed every day)
  ════════════════════════════════════════════════════════════════════════════

    • Comprehensive but not bloated. Every sentence earns its place.
    • NO size cap. NO line cap. Optimal length is whatever fully covers
      the topic. Expect 1,500–4,000 lines per day depending on content
      density. Do not artificially compress.
    • Java code: Java 21 idiomatic. Use records, var (sparingly), pattern
      matching, enhanced switch, Stream API where it improves clarity.
      Modern Spring Boot 3.x conventions when Spring-relevant.
    • Use code blocks (```java, ```yaml, ```sql, ```hcl etc.) for every
      code snippet, properly fenced.
    • Markdown tables for any comparison ≥ 3 items.
    • Inline external links at the point of mention; duplicate them in
      § 10 references.
    • DO NOT delegate to subagents — write inline.
    • DO NOT use emojis.
    • DO NOT use filler phrases ("Let's dive in", "Great question",
      "It's important to note"). Lead with content.
    • Use second person where instructional ("you'll see this when…").
    • Use first-person plural sparingly, only when describing collective
      engineering culture ("we treat L2 cache as a last resort").
    • Tier-tag every distinct sub-block with [BOTH] / [SENIOR IC] / [STAFF].
    • When tier diverges within a section, keep the [SENIOR IC] base and
      add [STAFF] extension as a separate sub-sub-section — do not blend.
